表是怎么生出来的：迁移脚本逐行读

目标：拿到一个 Flyway 迁移文件，能读出三件事——它做了什么、 为什么这么做、表设计如何反过来印证查询设计。

smart-square-chat/src/main/resources/db/migration/V1.0.10__add_chat_feedback_analysis.sql

一、先认识 Flyway：DDL 也要版本控制

表结构不能用"上去连库敲 ALTER"的方式维护——多人开发、多套环境，谁也不知道 某个环境现在的表长什么样。Flyway 的做法：所有 DDL 写成版本化脚本，按文件名顺序执行， 每张表只在 flyway_schema_history_chat 里记录一次"已执行"。

文件名即契约：V1.0.10__add_chat_feedback_analysis.sql = 版本号 V1.0.10 + 双下划线 + 描述。已执行的脚本禁止修改 （改了就对不上历史记录的校验和），要修正只能写 V1.0.11 新脚本—— 所以你会在仓库里看到 1.0.10 建表、1.0.11 打补丁这种模式。

二、第一段：幂等建表

DECLARE n INT;
BEGIN
    SELECT COUNT(*) INTO n FROM USER_TABLES
     WHERE TABLE_NAME = 'FM_SQUARE_CHAT_FEEDBACK';
    IF n = 0 THEN
        EXECUTE IMMEDIATE 'CREATE TABLE ...';
    END IF;
    ...
END;
/

脚本的头部注释写明设计意图：「独立反馈分析存储，不导入旧测试反馈，不级联删除会话快照」。

整段包在达梦 PL/SQL 匿名块里，先查数据字典 USER_TABLES 再建表—— 防御性幂等：Flyway 保证脚本只跑一次，但作者仍假设"可能有个老环境已经手工建过表"， 查一下再建，撞到旧库也不会报错中断。同一个块里后面还有三个同类判断： USER_INDEXES 查索引、USER_TAB_COLUMNS 查旧列 （把废弃的 MODIFIED_TIME 列删掉）。

读法：企业迁移脚本里 IF n = 0 THEN EXECUTE IMMEDIATE 这种壳子 不是啰嗦，是"环境不可信"的标准防护服。判断标准：脚本能否在任何状态的库上安全执行。

三、列设计：每个类型都在回答问题

ID               BIGINT IDENTITY(1,1) PRIMARY KEY,
ORG_CODE         VARCHAR(128) NOT NULL,
FEEDBACK         VARCHAR(8),              -- 可空：空=未评价/占位
PROBLEM_TYPES    VARCHAR(128),
NOTE             VARCHAR(1200),           -- 业务限300字
QUESTION_TEXT    CLOB,
ANSWER_TEXT      CLOB,
FIRST_FEEDBACK_TIME TIMESTAMP,
SNAPSHOT_TIME       TIMESTAMP NOT NULL,
设计回答的问题
IDENTITY(1,1)达梦的自增列语法（等价 MySQL AUTO_INCREMENT）， 对应实体里 @TableId(type = IdType.AUTO)
FEEDBACK 可空行可以"先占位、后填评价"——所以查询端必须 IS NOT NULL FEEDBACK 过滤，两课前后呼应
NOTE VARCHAR(1200)业务上限 300 字 × UTF-8 最多 4 字节/字 = 1200。 达梦默认按字节计 VARCHAR 长度（LENGTH_IN_CHAR=0）， 末尾注释专门解释了这点——脚本作者连库的字符集语义都考虑了
问答文本用 CLOBVARCHAR 有长度天花板，快照内容不定长 → 大对象类型， 用空间换"永远放得下"
没有外键关联会话/消息/智能体的列全是裸 VARCHAR。 快照表的哲学：故意不建 FK——原记录删了，快照行不受影响 （这就是 ASSOCIATION_STATUS 存在的原因）

四、索引是"查询需求的镜像"

CREATE UNIQUE INDEX UK_CHAT_FEEDBACK_RUN
    ON FM_SQUARE_CHAT_FEEDBACK (ORG_CODE, USER_ID, RUN_ID);
CREATE INDEX IX_CHAT_FEEDBACK_TIME
    ON FM_SQUARE_CHAT_FEEDBACK (ORG_CODE, FEEDBACK, FIRST_FEEDBACK_TIME, ID);
CREATE INDEX IX_CHAT_FEEDBACK_AGENT
    ON FM_SQUARE_CHAT_FEEDBACK (ORG_CODE, AGENT_PRODUCT_ID, FIRST_FEEDBACK_TIME, ID);

对照第 2 课 query() 的条件，三个索引各司其职：

索引服务谁列序逻辑
UK_* 唯一索引幂等兜底 + 提交查重(org, user, runId) 恰好是幂等键
IX_*_TIME列表/统计：组织内按评价过滤+时间范围等值列在前（ORG_CODE、FEEDBACK），范围列在后（时间）
IX_*_AGENT按智能体筛选的同一类查询同上，把 FEEDBACK 换成 AGENT_PRODUCT_ID
更正我上节课的一个说法：自测题里我说"唯一索引没有兜底"——其实 UK_CHAT_FEEDBACK_RUN 就是兜底：两个并发请求同时 insert，数据库层一定有一个被拒。但它只能保证"不产生重复行"， 给不出"同值重试放行 / 异值报不可修改"的语义——语义层只能由 Service 的 check-lock-check 完成。两道防线各自解决不同问题：索引管"数据不脏"，代码管"行为正确"。

复合索引的口诀：等值在前、范围在后、排序垫底。 ORG_CODE = ? AND FEEDBACK = ? AND FIRST_FEEDBACK_TIME >= ? AND < ? 这个查询形状，正好让等值条件先缩到小范围、范围列在索引内有序、 ID 垫底稳住倒序分页。

五、COMMENT ON：把文档写进数据库

建表后紧跟 23 行 COMMENT ON COLUMN ... IS '...'。 Navicat/DM 管理工具里直接显示字段含义，比只写在 wiki 里可靠—— 文档会过期，紧贴表结构的注释不会。注意 FEEDBACK 的注释 「最新评价，空表示已清除」，它解释了为什么查询端要过滤 NULL。

六、第二段：改别人的表也要防御

脚本末尾另一个匿名块处理 FM_SQUARE_CHAT_MESSAGE.FEEDBACK_NOTE： 查 ALL_TAB_COLUMNS 里该列当前 DATA_LENGTH， 小于 1200 才 MODIFY 扩容——只扩不缩、有就跳过。 一次迁移做两件事（建新表 + 修旧表），但每步都可安全重复。

自测

1. 为什么已执行的 Flyway 脚本禁止修改，要改只能写新版本？

2. NOTE VARCHAR(1200) 为什么不是 300？

3. 既然有 UK_CHAT_FEEDBACK_RUN 唯一索引，为什么还要 Service 层做幂等检查？

4. IX_CHAT_FEEDBACK_TIME (ORG_CODE, FEEDBACK, FIRST_FEEDBACK_TIME, ID) 的列序依据是？

动手任务（10 分钟）

  1. 在 smart-square-chat/src/main/resources/db/migration/ 里数一下 一共有多少个 V*.sql，找出 V1.0.11 做了什么 ——它就是"已执行脚本不可改、只能补丁"的活例子。
  2. 在 disql 里跑 SELECT INDEX_NAME, COLUMN_NAME FROM USER_IND_COLUMNS WHERE TABLE_NAME='FM_SQUARE_CHAT_FEEDBACK' ORDER BY INDEX_NAME, COLUMN_POSITION; 对照脚本验证三个索引真实存在。
  3. 合上脚本，凭记忆写出这张表的三个索引及其列序，再打开对照。
