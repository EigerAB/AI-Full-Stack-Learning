### 1、Java Lambda 需匹配函数式接口

**Java Lambda 需要匹配一个“函数式接口”类型**，也就是只有一个抽象方法的接口。这个接口规定参数和返回值的类型。

先自己定义一个简单接口：

```java
@FunctionalInterface
interface NameChecker {
    boolean check(String name);
}
```

它只有一个没有方法体的方法：

```java
boolean check(String name);
```

这种方法叫**抽象方法**。它规定：

- 方法接收一个 `String`。
- 方法必须返回一个 `boolean`。
- 具体如何判断，由实现者决定。

因为这个接口只有一个抽象方法，所以可以用 Lambda 提供实现：
```java
NameChecker checker = name -> name.startsWith("Java");
```

“需要匹配”就是说 Lambda 的参数和返回结果必须符合接口的要求。

但是我看到你的代码里.filter、.map等的这些方法没有匹配抽象方法啊？

```java
List<String> names = List.of("Java入门", "Python入门", "Java实战");
List<String> result = names.stream()
        .filter(name -> name.startsWith("Java"))
        .map(name -> name + "课程")
        .toList();
System.out.println(result);
```

以你的代码为例：

```
.filter(name -> name.startsWith("Java"))
```

在 VS Code 中可以这样查：

1. **悬停在 `filter` 上**，查看方法声明，会看到类似：
    
    ```
    Stream<T> filter(Predicate<? super T> predicate);
    ```
    
    暂时忽略 `? super T`，先抓住：参数类型是 **`Predicate`**。
    
2. 在 `filter` 上按 **F12** 跳转到定义，再对参数类型 **`Predicate`** 跳转到定义。
    
3. 在 `Predicate` 接口中找到：
    
    ```java
    boolean test(T t);
    ```
    
    它没有方法体，以分号结尾。接口中这种方法默认就是 `public abstract`，所以源码可以省略这两个关键字。

### 3、List初始化的方法

需先学习集合篇

|写法|增删元素|`set` 替换元素|
|---|---|---|
|`new ArrayList<>()`|可以|可以，索引必须已存在|
|`List.of(...)`|不可以|不可以|
|`Arrays.asList(...)`|不可以|可以|
|`new ArrayList<>(已有集合)`|可以|可以|
|`stream.toList()`|不可以|不可以|
最后注意一个与泛型有关的坑：**`int[]` 不能通过 `Arrays.asList` 自动变成整数列表。**

```
int[] numbers = {1, 2, 3};

List<int[]> wrong = Arrays.asList(numbers);
System.out.println(wrong.size()); // 1，整个数组被当作一个元素
```

应当这样转换：

```
List<Integer> numbersList = Arrays.stream(numbers)
        .boxed()
        .toList();
```

`boxed()` 把流中的 `int` 转成 `Integer`。

平时可以先记三种：**空的可修改列表用 `new ArrayList<>()`，固定内容用 `List.of(...)`，对象数组转可修改列表用 `new ArrayList<>(Arrays.asList(array))`。**



### 4、AOP和抽离公共代码的区别

如果我在oop中用一个公共能力的代码 + 发布订阅模式，完全也能实现AOP的功能啊？

#### 公共方法抽调：逻辑复用了，但调用位置还要自己安排

你可以抽取计时代码：

```java
public void createProduct() {
    long start = System.nanoTime();
    try {
        // 创建产品
    } finally {
        TimingLogger.log("createProduct", start);
    }
}
```

`TimingLogger.log()` 的实现只有一份，但如果 50 个方法都需要统计耗时，每个方法仍要安排开始计时、结束记录。

也可以进一步封装成：

```java
public void createProduct() {
    Timing.measure("createProduct", () -> {
        // 创建产品
    });
}
```

这里的 Lambda 表示“把创建产品的操作交给 `measure` 执行”。这是示意写法，`Timing.measure` 需要自己实现。

这样已经很好地减少了重复。但每个需要计时的方法，仍然需要主动使用这个包装。

但发布订阅本身并不会自动发现“某个方法即将执行、已经返回或抛出了异常”。如果要靠事件统计任意方法的耗时，你仍需要安排：

```
方法开始 → 发布开始事件
方法结束 → 发布结束事件
方法异常 → 发布失败事件
```

这些事件可以由业务代码发布，也可以由统一包装器发布。**关键问题仍是：谁负责在正确的位置触发它们？**

另外，发布订阅可以是同步的，也可以是异步的；它本身并不等于异步处理。

#### AOP：统一安排“哪些方法，在什么时候执行公共逻辑”

AOP 可以表达这样的规则：

> 对指定 Service 中匹配的方法，在执行前开始计时，在执行结束时记录耗时。

于是业务方法可以保持：

```
public void createProduct() {
    // 创建产品
}
```

调用过程则由 Spring AOP 的代理组织：

```
调用方
  ↓
代理：开始计时
  ↓
业务方法：创建产品
  ↓
代理：记录耗时，包括异常结束的情况
```

这里把两件事集中到了业务方法之外：

|集中管理的内容|AOP 中的名称|
|---|---|
|对哪些方法生效|Pointcut，切点|
|在这些位置执行什么公共处理|Advice，增强逻辑|

所以 AOP 不只是“把计时代码抽到公共类里”，还把**计时代码与业务方法的连接规则**抽出来了。


#### 总结

OOP面向对象编程，针对业务处理过程的实体及其属性和行为进行抽象封装，以获得更加清晰高效的逻辑单元划分。

而AOP则是针对业务处理过程中的**切面**进行提取，它所面对的是处理过程的某个步骤或阶段，以获得逻辑过程的中各部分之间低耦合的隔离效果。

这两种设计思想在目标上有着本质的差异。
