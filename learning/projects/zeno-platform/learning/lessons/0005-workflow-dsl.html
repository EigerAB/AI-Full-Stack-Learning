Workflow DSL + 节点执行器——工作流怎么被画出来、跑起来

阅读约 12 分钟 · 主源 core/agent/workflow_dsl.py · ← 上一课

下一节：第 6 课 · SubAgent / Team runtime →

上一课看了工具执行层：AgentLoop 怎么拿到 ToolExecutionResult，并把它再喂回模型。下一步我们往上走一层，看看更大的“画布式工作流”是怎么定义的——DSL 描述了哪些节点、哪些边、哪些变量；节点执行器 决定每种节点如何真正执行。这个层面是你遇到「节点没跑」「分支不走」「变量没写回」等故障时，最容易看错的地方。

先给结论：工作流不是“脚本”，而是“节点图”

主源：zeno-backend-agent/core/agent/workflow_dsl.py · build_default_workflow_dsl 第 105 行
{
  "version": "1.0",
  "meta": {"skeleton": "default_v1"},
  "nodes": [
    {"id": "begin_1", "type": "Begin", "data": {"mode": "conversational"}},
    {"id": "agent_1", "type": "Agent", "data": {...}},
    {"id": "reply_1", "type": "Reply", "data": {...}}
  ],
  "edges": [
    {"source": "begin_1", "target": "agent_1"},
    {"source": "agent_1", "target": "reply_1", "sourceHandle": "start"}
  ]
}

这段是默认骨架：Begin → Agent → Reply。一张工作流图的核心不是代码分支，而是：nodes 里每一个节点是谁，edges 里哪条边连到哪条边，节点的 data 里放变量、提示词、模型参数、输出格式。真正跑起来时，调度器按图遍历，节点执行器按 type 做不同动作。

一句话概括

DSL 决定“图长什么样”，节点执行器决定“每个节点怎么跑”，调度器决定“按边从哪到哪”。排障时，先看图结构，再看节点实现，最后看变量和值是否落回图里。

DSL 里最重要的两件事：节点类型 + 图结构校验

core/agent/workflow_dsl.py · ALLOWED_NODE_TYPES 第 90 行，validate_workflow_dsl 第 193 行
ALLOWED_NODE_TYPES = frozenset(NODE_REGISTRY)

# 例：Begin / Agent / Reply / End / KnowledgeRetrieval / ... / Loop / LoopBreak

这不是“随便一堆 key”。它来自 core/agent/workflow_node_registry.py 的 NODE_REGISTRY。也就是说，合法节点种类是注册表驱动的，新增节点类型必须同步注册、同步校验器。

validate_workflow_dsl() 做的事是：检查：

  • version 是否为 "1.0"
  • nodes 是不是非空 list
  • edges 是不是 list
  • 每个节点的 id 是否填了、是否重复
  • type 是否在允许集合里
  • 节点自己的 data 是否符合某个节点类型的字段要求
  • 循环节点/问答节点/子工作流节点之类的图约束是否满足

这里的关键是：校验器不是只做最表层检查。它会调用 validate_extended_node_data(node_type, data, display, dsl=dsl) 这类函数，按节点类型细分验证字段，像 Agent 节点的 llm_id、max_rounds、exception_method，或者循环节点的 loop_type。如果节点类型不合法，你在画布或者调试时，最早就会被拦住。

「为什么某个节点能画出来，但运行时报错」——大概率是图结构合法，但该节点的 data 字段不满足具体节点校验；或者它在循环体内被放了不该放的类型。先看 validate_workflow_dsl，别一上来就看执行器。

节点类型：不是“一个 AI 节点”，而是一类执行器

core/agent/workflow_node_registry.py · NODE_REGISTRY 与 NodeSpec

真正的工作流引擎里，每个节点类型都被包装成 NodeSpec，其中包括：

  • type：节点类别
  • title：在画布里显示的名字
  • execute：真正运行时调用的函数
  • validate：字段级校验器
  • 一些节点特有的约束，比如 forbidden_in_loop

workflow_node_executors.py 把 29 个节点的真正执行闭包放在这里，名字形如 _exec_begin、_exec_switch、_exec_tool_call、_exec_loop、_exec_agent。这些函数不是“随便实现”，而是对既有 agent_workflow_debug.py 中 debug 执行器的转发。

async def _exec_begin(ctx: NodeExecContext) -> NodeExecResult:
    from core.agent.agent_workflow_debug import _debug_begin
    return _debug_begin(...)

async def _exec_agent(ctx: NodeExecContext) -> NodeExecResult:
    from core.agent.agent_workflow_debug import _debug_agent
    return await _debug_agent(...)

这层设计很重要：注册表把节点维度统一起来，调试器和正式执行器都复用同一套节点实现。如果你在调试某个节点时，能看到它在 workflow_node_executors.py 里被转发到某个 _debug_* 函数，就能直接追到真正行为。

执行是图遍历，不是“顺序代码”

core/agent/agent_workflow_debug.py / core/agent/agent_workflow_graph_runner.py

工作流图运行时通常是这样：

  1. 固定起点节点（如 Begin）
  2. 按 edges 找下一个节点
  3. 执行该节点的 execute 函数，拿回输出变量
  4. 把输出写回变量池（variables）
  5. 继续走出边，直到 End 或分支结束

也就是说，一个工作流不是“if-else 语句堆”，而是“图 + 变量池 + 节点执行器”。最容易出错的是：边没连上、分支没命中、节点返回值没写回变量、循环控制节点放错了位置。这些都不是 LLM 的问题，而是图结构和节点语义的问题。

循环节点和循环控制节点：最容易搞错的一类边界

core/agent/workflow_dsl.py · LOOP_CONTROL_NODE_TYPES / LOOP_FORBIDDEN_BODY_TYPES
LOOP_CONTROL_NODE_TYPES = frozenset({"LoopStart", "LoopEnd", "LoopBreak", "LoopContinue"})
LOOP_FORBIDDEN_BODY_TYPES = frozenset(
    node_type for node_type, spec in NODE_REGISTRY.items() if spec.forbidden_in_loop
)

这块的意思是：循环体里不能塞某些“非法”节点类型。比如：

  • LoopBreak / LoopContinue 只能在循环体内
  • 某些节点，像终端节点、暂停节点、嵌套循环，不能被直接放进循环体

这不是微观实现细节，而是“图合法性”的一部分。很多流程图看起来能跑，实际上分支或循环出边不对，或者循环体里混进了非循环允许节点，会导致图一次运行就停掉，或者变量只在循环内部维护，最终没有返回。

Agent 节点：工作流里最核心的那个节点

core/agent/workflow_dsl.py · validate_agent_node_data、build_default_workflow_dsl

默认骨架里，最关键的是 Agent 节点。它的数据里会有：

  • sys_prompt
  • llm_id
  • prompts
  • message_history_window_size
  • max_rounds
  • exception_method
  • 采样参数：temperature、top_p 等

这里是图真正“启用大模型”之处。它不像单轮 AgentLoop 那样一刀切，而是把模型能力、回合限制、系统提示和异常处理配置都放进这个节点。工作流故障经常不是大模型本身失败，而是 Agent 节点的配置不对：prompt 空、llm_id 缺、max_rounds 太低、exception_method 走错出口。

排障归因表（增量）

症状 最可能落点 确认方式
节点能画，但运行时报错 validate_workflow_dsl() / 某节点的 data 校验 看该节点的字段是不是缺、是不是类型不对、是不是循环体非法
图走不动，没下一步 边没连、source/target 不合法、流向不匹配 看 edges 和起终点是否形成通路；检查 Begin → ... → End
循环里调试不了，变量丢了 循环控制节点或禁止节点类型混进了循环体 对照 LOOP_CONTROL_NODE_TYPES 与 LOOP_FORBIDDEN_BODY_TYPES
大模型节点不调模型 Agent 节点的配置字段错误 查 llm_id、sys_prompt、prompts、max_rounds
变量出现“设置了但没用上” 节点输出没写回变量池，或下游引用写法不对 看节点执行器返回值、输出键名，以及上游引用变量名是否一致

检索检验

排障检验

一个工作流里，Agent 节点配置正确，但它的下游连接不是 Reply、而是一个合法但没被正确命中的分支。结果是图跑到一半停住，日志里看不到明确异常。更像是哪个层面的故障？

  • 工具层 failed，查 core/tool/executor.py 的 is_error 判定
  • 图结构 / 节点执行流层，查 workflow_dsl.py 和 edges / 节点路由
  • 大模型 provider 层，查 core/llm 里模型连接
  • 前端 HTTP 层，查 SSE 是不是断了

这类“看起来没报错但流程停住”的问题，最像是工作流图结构问题：节点配置可能是对的，但图的边、分支、循环体、输出变量没走成，导致程序在图遍历阶段卡住。真正要查的，是 workflow_dsl.py 的校验和图连接、以及节点执行器的 return / variables 更新，而不是工具层。本课的关键就是：先读图，再看节点。
