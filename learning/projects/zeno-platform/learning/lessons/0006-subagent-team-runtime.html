SubAgent / Team runtime——多智能体不是放大单循环，而是另起 context

下一节：第 7 课 · 事件流 / SSE wire（待续）

上一课看了工作流图：workflow_dsl.py 只负责定义图和校验，真正执行依靠节点执行器。到了第 6 课，我们再往上一层看：多智能体不只是“在同一个 AgentLoop 里多跑几轮”，而是另起一个子上下文 / 一个 team runtime。这也是「同样的工具，为什么一条链路里总能串到子代理，父级却没收到想要的结果」的关键位置。

先给结论：SubAgent 与 Team 的核心区别

一句话概括

SubAgent：单个子代理，独立 ExecutionContext，继承/过滤父级工具，拿到自己的结果再回到父级；Team：多个已存在的 AgentInstance 成员以团队模式并发或协作执行，协调器做 wave / task / summary。

你不能把它们当成“只多了一层抽象”。在这套代码里，它们分别对应不同的运行器：SubagentRunner 和 TeamRuntime。前者解决的是“一个父级任务拆成一个子任务”，后者解决的是“一个任务拆成多个成员协作”。

SubAgent：另起一个独立执行上下文

主源：zeno-backend-agent/core/agent/execution/subagent/runner.py · SubagentRunner._create_child_context 与 run
SubagentRunner.run(agent_type, prompt, parent_context)
  ├─ definition = self._resolve_definition(agent_type)
  ├─ child_context = self._create_child_context(definition, prompt, parent_context)
  │   ├─ tools = 继承父级工具 / 过滤 agent 工具 / 按 definition.tools 白名单
  │   ├─ child_agent_id = f"{parent.agent_id}::{definition.name}"
  │   ├─ extra = replace(parent.extra, usage_tracker=None)
  │   └─ model_name / system_prompt / usage_tracker / broadcaster_agent_id：全另起一套
  ├─ loop = AgentLoop(config=LoopConfig(...))
  └─ async for event in loop.run() ...

这里的核心不是“把同一个上下文拿来复用”，而是复制一份新的执行上下文。代码里最关键的几个点：

  • definition.tools is None：继承父级工具列表，但自动排除 agent 工具，防止递归派生子代理；
  • definition.tools == []：纯文本推理，没有工具；
  • parent.agent_id 会变成 f"{parent.agent_id}::{definition.name}"，这样前端/日志能区分父子；
  • 新建 usage_tracker，并且 extra = replace(parent.extra, usage_tracker=None)，避免把父级的计费状态串过去；
  • broadcaster_agent_id=child_agent_id，让流式事件带有子代理身份标识。

这里的“问题入口”通常不是模型本身，而是上下文隔离不彻底：工具继承错误、agent_id 串了、子代理事件没有带 subagent_id、父级拿不到最终结果。一次子代理跑起来，很大概率是因为 parent_context 的共享状态被错误继承了，或者白名单过滤把本该用的工具剥掉了。

如果你看到「子代理能生成内容，但父级工具结果不对」「一个 agent 的输出被混入另一个 agent 的事件流」，优先看 SubagentRunner._create_child_context()、child_agent_id、以及 `extra_data.subagent_id / parent_tool_use_id`。

子代理的消息和事件：不是直接写回父级，而是挂在 tool result 上

zeno-backend-agent/core/agent/execution/subagent/runner.py · run() 中的消息持久化与 ContentHandler

在 SubagentRunner.run() 里，代码会为子代理创建 user 和 assistant 占位消息，并写上：

  • subagent_id
  • parent_tool_use_id

注意这里的设计非常有代表性：子代理并不是把逐步思考直接塞回父级消息流，而是让父级最后只接收最终文本作为 tool_result。也就是说，子代理的完整过程可以被前端查看，但父节点只拿到一个结果摘要，而不是一整段嵌套事件流。这个设计非常接近“工具调用”语义。

# 伪代码：父级只接收最终文本，完整过程保留在子代理消息/事件里
final_text = subagent_result.content
tool_result = {"type": "subagent", "content": final_text, ...}

这会导致两个很典型的问题：

  1. 前端看见子代理卡片，但父级回调没有正确映射；
  2. 消息持久化里，subagent_id / parent_tool_use_id 丢了，日志看起来像“同级消息”混在一起。

Team runtime：多个 AgentInstance 作为成员协作，不是子代理的简单复用

主源：zeno-backend-agent/core/agent/execution/team/runtime.py / core/agent/execution/team/coordinator.py

TeamRuntime 不是某个子代理的包装，而是一个“团队执行器”。它从 config 里解析 multi_agent.workers，拿出成员列表，并把他们转成 TeamMemberSpec / TeamMemberRef。关键逻辑在 extract_team_member_specs() 和 extract_team_max_concurrent_workers() 中。

multi_agent = _extract_multi_agent_config(config)
workers = multi_agent.get("workers") or []
for raw_worker in workers:
    agent_id = _worker_agent_id(worker)
    alias = worker.get("alias") or worker.get("name") or agent_id
    specs.append(TeamMemberSpec(alias=alias, agent_id=agent_id))

这表示：Team runtime 不是用新建子代理的方式串起成员，而是使用已有的 AgentInstance 作为成员。因此团队模式最容易出错的地方不是“模型配置”，而是：

  • 成员配置没解析出来；
  • 同名 alias duplicated；
  • 成员没有真正拿到 agent_id；
  • 并发 worker 数/任务分配策略和 team runtime 的 wave 逻辑不匹配。

在这个层面，排障时你要把焦点转到成员解析 + 分配 + 协调，而不是单个 AgentLoop。也就是说，Team 问题往往不是“单轮 LLM 输出错了”，而是“队列怎么排、成员怎么分配、哪个成员被错误复用、哪个 wave 的事件走丢了”。

SubAgent 和 Team 的共同故障面：成员/上下文/事件没有“同一套身份”

zeno-backend-agent/core/agent/execution/__init__.py 与 core/agent/execution/team/runtime.py

如果你把 SubAgent 和 Team 放在一起看，最典型的共性是：它们都需要明确的身份和上下文边界。没有统一约定，几乎所有异步多智能体排障都退化成“哪边消息看起来串了、谁负责最终输出、哪个 agent_id 参与了计算”。

代码里已经体现了这一点：

  • SubAgent: agent_id 改成 parent_agent_id::subagent_name
  • Team: 通过 alias / agent_id / TeamMemberRef 标识成员
  • 事件总线带 broadcaster_agent_id / subagent_id / parent_tool_use_id

换句话说，多智能体的“对错”不在于是否能新开一个线程，而在于各个成员的上下文、身份、事件和最终总结是否一一对应。这是很多“看起来像模型不行”的问题的真实根因。

检索检验

排障检验

你看到一个子代理事件能流出，但父级在最终结果里看不到它的输出，且日志里 agent_id 也异常。最先应查哪一处？

  • HTTP route 层，看聊天接口是不是没有处理流
  • SubagentRunner._create_child_context() 和 run() 里的 identity / metadata / tool result 回传
  • RAG 检索服务，看知识库是不是返回空
  • 单轮 AgentLoop 的 while True，看是否无工具调用

这个症状的本质往往不是“LLM 没输出”，而是“子代理上下文和父级事件流没有对齐”。多智能体排障最先要查的是 identity、上下文隔离、以及父级对子代理结果的回传，而不是前端或 RAG 的表层问题。

推荐主源

zeno-backend-agent/core/agent/execution/subagent/runner.py · SubagentRunner._create_child_context / run
zeno-backend-agent/core/agent/execution/team/runtime.py · extract_team_member_specs / TeamRuntime

如果你要做“多智能体排障”，最值得按这个顺序去追：先看子代理是否另起了 child context，再看它有没有写好 subagent_id / parent_tool_use_id；然后再看 team runtime 有没有成功从 config 中解析出成员与 worker 配置。这样你就不会把多智能体问题误判成单循环或大模型问题。
