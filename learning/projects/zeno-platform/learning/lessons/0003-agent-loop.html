AgentLoop——LLM ↔ Tool ↔ Repeat 的核心引擎

阅读约 12 分钟 · 主源 core/agent/execution/loop.py · ← 上一课

上一课的终点是 _run_agent_scoped 阶段 2.3：Agent.chat。这一课我们钻进去，看一轮对话真正「跑」起来的地方——AgentLoop。它是所有执行模式（单循环 / Subagent / Team / Plan）共享的唯一引擎，也是「回复内容不对」「工具没调」「跑着跑着空了」这类故障的最终落点。

先纠正一个路径

第 2 课的归因表里写「core/agent/（下一课）」。准确说，AgentLoop 不在 core/agent/base.py，而在 core/agent/execution/loop.py。base.py 里的 Agent 类是外壳——它准备上下文、建一个 AgentLoop 实例、调 loop.run()、再把 yield 出来的事件路由给 SSE。真正「LLM → 工具 → 重复」的循环体在 execution/loop.py。

记住这个形状：每轮 = 一次 LLM 调用 +（可能有）一次工具执行。llm_rounds 在 LLM 调用成功后 +1（loop.py:502），不是在工具执行后。所以「max_turns=30」意味着最多 30 次 LLM 调用。

五种终止——和它们对应的症状

这是排障时最该背的一张表。loop 只有 5 种方式退出 while True，每种产出一个 RESULT 事件，subtype 字段就是答案：

subtype 触发条件 行号 典型症状
success LLM 无工具调用且有正文 586 正常结束
error_max_turns llm_rounds ≥ max_turns 383 「跑了很多轮还没停」/ 工具反复调
error_max_budget_usd 超费用预算 390 / 492 跑到一半被费用门掐了
error_during_execution LLM 抛异常 / 工具执行抛异常 / 空回复重试仍空 474 / 712 / 571 SSE 收到 error 事件，有异常类名
error_no_model context.model_name 为空 342 「空 run」：llm_calls=0、model=unknown

（还有 suspended——AG-UI 前端动作工具挂起，不是错误，本次 run 正常收尾等续跑。）

🔴 最大的坑：错误判据是 subtype，不是 exception

这是这个 loop 里最容易误判的地方，也是线上「成功的空 run」问题的根因。

core/agent/errors.py · run_error_from_result 第 54 行

AgentLoop._make_result（loop.py:1958）只在被传入 Exception 时才往结果里加 error 键。但 5 条失败返回里有 4 条不传 Exception：无模型、max_turns、max_budget×2、工具执行失败。如果上层用「有没有 error 键」判断失败，这 4 条全部漏判——消息落 completed、AG-UI 不发 event: error，前端只看到 RUN_STARTED → RUN_FINISHED，零错误线索。

正确的判据是 subtype.startswith("error_")（errors.py:80）。_execute_inner 用的就是 run_error_from_result，它优先取富信息 error 键（带真实异常类名），没有就回退到 subtype。

排障「用户说 AI 没回复，但前端显示已完成、后端日志也没 error」时，别看 error 日志，看 RESULT 事件的 subtype。多半是 error_no_model（租户上下文丢失 / connection 解析失败）或 error_max_turns（工具死循环）。这条判据就是为了给「空 run」一个可指认的分支标识而专门拆出来的。

三个「不一样」的细节

1. 没有 provider fallback 了

loop.py:175 的注释写得很直白：2026-07-22 的「全删回退」移除了跨厂商/跨模型的容错切换。_llm_call_single（loop.py:1284）现在单模型单次调用，失败直接上抛，由 run() 的 except 分支捕获回传。这意味着「配 A 跑 B」在这套代码里结构上不可能——如果日志里看到模型名和配置不一致，问题在 _prepare_execution 解析阶段，不在 loop 里。

2. 单个工具失败 ≠ 循环终止

这是和很多人直觉相反的一点。_execute_tools 返回 dict[str, ToolExecutionResult]，每个结果有 is_error 标志（loop.py:674）。单个工具 is_error=True 不会终止循环——错误结果照常追加进消息历史，模型可以读到错误并自行修正。只有 _execute_tools 本身抛异常（比如 tool_executor 没配置、批量调度崩了）才走 except 分支终止（loop.py:698-713）。

「工具报错了但 AI 还在继续跑」是正常行为，不是 bug。模型会读到 {"type":"tool_result","is_error":true,"content":"..."} 并决定重试或换方案。只有「工具报错后 AI 立刻停了」才要看是不是 _execute_tools 抛了异常。

3. 空回复守卫：绝不静默 SUCCESS

loop.py:535 的 _has_visible_output 只看 content 是否非空字符串——thinking 不算（对用户不可见）。如果一轮既没正文也没合法工具调用（多半是模型把答案写进了 reasoning 就 stop），loop 会注入一段提示让模型「把话说出来」，重试 1 次；仍空就抛 EmptyModelResponseError 收尾成 ERROR_EXECUTION。绝不把它当 SUCCESS 静默结束——否则用户会拿到一条空的「已完成」。

流式 vs 非流式

由 LoopConfig.enable_stream 控制（默认 True）。差别只在第 ② 阶段的 LLM 调用怎么 yield：

  • 流式：_llm_stream_single 在 LLM 生成过程中逐块 yield LLM_THINKING_DELTA / LLM_CONTENT_DELTA / LLM_TOOL_USE_START / LLM_TOOL_INPUT_DELTA，最后 yield 一个 LLMResponse 对象。_execute_inner 把这些 delta 路由给 stream_handler（content_handler）→ EventBroadcaster → SSE，前端就能看到字一个个冒出来。
  • 非流式：_llm_call_single 一次性返回 LLMResponse，只在有 thinking 时 yield 一个 thinking delta。前端要等整段生成完才看到。

两种模式共用同一个 while True 循环体，终止条件、工具执行、错误处理完全一样。浏览器面（HTTP）走的是流式——所以你在前端看到的「思考中…」字样就是 LLM_THINKING_DELTA 事件实时渲染的结果。

检索检验

排障检验

用户反馈：AI 回复了一条空消息，前端显示「已完成」，后端日志里没有任何 error 级别记录，也没有异常堆栈。SSE 流里有 RUN_STARTED 和 RUN_FINISHED 但中间没有 content delta。最该先看什么？

  • 翻 LLM 调用失败的 error 日志，找异常类名
  • 查 _execute_tools 抛没抛异常，看工具执行日志
  • 看 RESULT 事件的 subtype 字段，大概率是 error_no_model
  • 查 BeforeToolUse hook 是不是 BLOCK 了所有工具

关键线索：「无 error 日志、无异常堆栈、无 content delta、却显示已完成」正是「成功的空 run」的典型表现。loop 里 4 条失败路径不传 Exception，按「有没有 error 键」会全部漏判，只有 subtype 才指认得到。无 content delta 说明 LLM 根本没被调起来（否则流式会有 delta），这指向 error_no_model——model_name 为空，loop.py:342 直接 yield 结果返回。下一步查 _prepare_execution 里 model_name 怎么解析的（租户上下文丢失 / connection 解析失败）。如果 subtype 是 error_max_turns 则会有多轮 LLM 调用记录，和「无 delta」不符。
