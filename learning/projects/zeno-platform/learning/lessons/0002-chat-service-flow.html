chat_service 的 10 步流程——从 HTTP 进 services 的第一跳

阅读约 10 分钟 · 主源：services/chat_service.py · ← 上一课

上一课你看到了 HTTP 路由层：POST /chat 调 chat_service.submit()，后者就是 chat(stream=False, _await_agent=False) 的别名。这一课我们走进 chat() 这个 2900 行函数——它是所有对话的必经之路，不管从 HTTP 还是 gRPC 进来都汇到这里。

函数虽然长，但结构是清晰的 10 步。你排障时要做的，就是根据症状判断卡在哪一步。

步骤 1-2：验证与对话归属

第 1 步检查 agent 是否存在、状态是否可运行。第 2 步创建或校验 Conversation——这里有个容易踩的归属校验：

services/chat_service.py · 第 2584 行
if not is_new_conversation and bound_agent_id and bound_agent_id != pool_key:
    raise ValueError("该会话属于其他智能体，请开启新会话")

一个会话创建时就绑定了 agent_id，后续轮次换了 agent 会被拒。排障时如果用户反馈「续接对话报错」，先确认前端有没有传对 agent_id。

步骤 4：文件处理的两条路

这是这个项目不一样的地方。文件引用有两种形态，走两条不同的消费路径：

关键区分

URL 引用（file_url）：直接传给模型，模型自己决定要不要看。
storage_key 引用：服务端校验归属（前缀匹配用户目录）→ 重签 presigned URL → 传给绑定工作流消费（工作流节点拿的是重签后的 URL）。

两者不互斥：同一个文件可以同时走两条路。但如果你排障「工作流拿不到文件」，先查前端传的是 storage_key 还是裸 file_url——后者工作流消费不到。

步骤 5.5：BEFORE_DISPATCH hook

在标准化消息之后、创建 Session 之前，有一个 BEFORE_DISPATCH 钩子。它可以做两件事：

  • BLOCK：拦截消息，返回 {status: "blocked"} 或 yield 一条 error 事件。
  • MODIFY：改写消息内容。
如果用户反馈「消息发出去就被拒了，但不是 4xx」，查一下有没有装 BEFORE_DISPATCH hook 在拦——它的拦截走的是正常返回路径，不是 HTTP 异常。

步骤 6-8：Session 与消息持久化

第 6 步先检查并发（session_pool.check_can_create_session），再创建 Session。第 7、8 步保存用户消息和 Assistant 占位。

这里有个值得注意的 DB session 拆分：

services/chat_service.py · 第 2740-2743 行
# 注意：MessageRepo.create_message 内部会 commit。
# 这里将 user / assistant 写入拆成两个独立 session，
# 避免同一 session 在多次 commit 后连接重取导致租户 search_path 漂移。

这是多租户架构的细节：search_path 是连接级的，commit 后连接可能被池重取，重取的连接不带 search_path。所以每条消息用独立的 DB session。排障时如果看到「消息写到了错的租户 schema」，查这条线。

第 7-8 步失败会清理已创建的 Session（end_session(status="failed")）并抛 ValueError。

步骤 9：资源准备——detached 的分水岭

这是整个函数最关键的分叉点。第 2792 行：

if (not stream) and (not _await_agent):
    _detached_task = asyncio.create_task(
        self._prepare_then_run_detached(...)
    )
    self._session_tasks.register(session_id, _detached_task)
    return {
        "task_id": session_id,
        "conversation_id": conversation_id,
        "message_id": assistant_message_id,
        "status": "running",
    }

两段式的 submit() 走的就是这条：stream=False, _await_agent=False → 把步骤 9（资源准备）和步骤 10（执行 Agent）整段塞进一个后台 asyncio.Task，立即返回 session_id。

这意味着：资源准备失败不会抛给 HTTP 调用方——submit 已经返回了。失败怎么通知前端？走进度流：

services/chat_service.py · _prepare_then_run_detached 第 3107 行起
except MCPRequiredError:
    await self._emit_prepare_error(
        session_id, conversation_id,
        "mcp_required",
        "所需 MCP 服务不可用，请检查 MCP 配置后重试",
    )
    return
except Exception:
    # _prepare_agent_for_session 已记录日志并完成清理；
    # 此处只负责经进度流通知前端。
    await self._emit_prepare_error(
        session_id, conversation_id,
        "resource_error",
        "资源准备失败，请稍后重试",
    )
    return
这是排障里最容易误判的一类故障：前端看到 Phase 1 成功返回了 session_id，但 Phase 2 SSE 流里第一条就是 error 事件，说「资源准备失败」。你会以为是 Agent 执行出错，其实是步骤 9 的 MCP 建连或 Agent 获取失败。看 error_type 字段：mcp_required vs resource_error 能帮你区分。

步骤 10：三种执行模式

模式 条件 行为 谁用
detached not stream and not _await_agent create_task，立即返回 HTTP submit() / gRPC 非流式
同步 not stream and _await_agent await _run_agent，等跑完 内部调用 / API 集成
流式 stream 返回 AsyncGenerator gRPC ChatStream / 旧 SSE

注意：浏览器面（HTTP）的对话只走 detached。流式模式主要是 gRPC 在用。

_run_agent 的三个阶段

步骤 10 最终调 _run_agent（第 3978 行），它再调 _run_agent_scoped（第 3995 行）。后者分三个阶段：

阶段 1: 数据准备
  1.1 加载历史消息（会话级缓存 + DB）
      ⚠ AG-UI 挂起续跑：resume_messages 非空时整份替换，不拼接
  1.2 前端变量由 VariablesInjector 在 ContextEngine.build 中注入

阶段 2: 执行 Agent
  2.1 发送 message_start 事件
  2.2 上下文管理（裁剪历史消息）
  2.3 调用 Agent.chat  ← 这里才真正进 core/agent/

阶段 3: 完成处理
  3.1 检查最终状态
  3.2 发送完成事件
  3.3 执行后台任务（如标题生成）
  3.4 释放资源（Agent、更新池状态）

阶段 2.3 的 Agent.chat 是进 core/agent/ 的入口——下一课讲 AgentLoop 时就从这里接。

检索检查

排障检索

用户反馈：点发送后页面正常显示了「AI 正在思考」，但几秒后弹出「资源准备失败，请稍后重试」。Phase 1 返回了 session_id，没有 4xx/5xx。故障最可能卡在 10 步的哪一步？

  • 步骤 1-2：agent 校验或对话归属校验失败
  • 步骤 7-8：消息保存失败导致 Session 被清理
  • 步骤 9：detached 后台任务里 MCP 建连或 Agent 获取失败
  • 步骤 10：_run_agent 阶段 2.3 调 Agent.chat 时出错

关键线索：「AI 正在思考」说明 Phase 1 成功返回了 session_id（步骤 1-8 都过了），前端已经开了 SSE 订阅。错误消息「资源准备失败」是 _prepare_then_run_detached 里 _emit_prepare_error 发出的——它在步骤 9 的 _prepare_agent_for_session 抛异常时触发。如果是步骤 10 的 Agent.chat 出错，错误会从 AgentLoop 内部上报，不会带「资源准备失败」这个措辞。所以答案是步骤 9。下一步看 error_type：mcp_required 查 MCP 配置，resource_error 查 AgentPool / 日志堆栈。
