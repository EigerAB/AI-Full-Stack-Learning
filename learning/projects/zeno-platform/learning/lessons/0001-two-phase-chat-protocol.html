两段式对话协议——排障的起点

阅读约 8 分钟 · 主源：http_server/routers/chat.py

你前端精通，所以先不讲 SSE 是什么。这一课只讲一件事：在这个项目里，一次对话从浏览器到 Agent 引擎，入口长什么样、为什么是这个样子。这是后面所有排障的起点——报错也好、回复不对也好，你都得先知道请求是从哪个门进来的。

为什么是「两段式」

大多数 FastAPI 教程里，流式接口是一个 POST /chat 直接返回 StreamingResponse，请求挂着等流完。这个项目不这么干。它把一次对话拆成两个 HTTP 调用：

  1. Phase 1 — 提交：POST /api/v1/chat，立即返回一个 session_id，不等 Agent 跑完。
  2. Phase 2 — 订阅：GET /api/v1/chat/{session_id}/progress，SSE 流，拿历史事件 + 实时事件。

为什么拆？因为 Agent 一轮可能跑几十秒甚至几分钟（LLM 调用、工具执行、子代理……）。一个 HTTP 连接挂这么久，中间任何一跳网关/代理超时都会断。拆开后，Phase 1 几乎瞬间返回，Phase 2 是纯只读订阅，断了能用 Last-Event-ID 重连，不丢事件。

排障时第一个要确认的就是：症状出在 Phase 1 还是 Phase 2？「提交没反应」和「流断了」是完全不同的故障域——前者在 chat_service.submit() 之前，后者在 session_service.reconnect_event_stream() 那条线。

Phase 1 的代码骨架

主源：zeno-backend-agent/http_server/routers/chat.py · 第 176–198 行
@router.post("", response_model=APIResponse[ChatSubmitResult])
async def submit_chat(
    body: ChatSubmitRequest,
    auth: AuthDep,
    _tenant: TenantContextDep,
) -> APIResponse[ChatSubmitResult]:
    from http_server.idempotency import run_idempotent_http

    data = await run_idempotent_http(
        domain="chat",
        idem_key=body.idempotency_key,
        user_id=auth.sub,
        ttl_config_key="chat_idempotency",
        execute=lambda: _do_submit(body, auth.sub),
    )
    return APIResponse.success(ChatSubmitResult(**data))

这个函数很短，但信息密度高。逐行看：

三个参数 = 三道门

body: ChatSubmitRequest 是请求体，FastAPI 自动按 Pydantic schema 校验——字段不对直接 422，根本进不了函数体。你排障看到 422，先去看 ChatSubmitRequest 的字段定义（同文件第 38 行起），别去翻 service。

auth: AuthDep 是鉴权依赖。AuthDep 的定义在第 35 行：

AuthDep = Annotated[AdminTokenPayload, Depends(require_access_token)]

这是 FastAPI 的 Annotated[..., Depends(...)] 写法——require_access_token 是个函数（http_server/dependencies.py 第 256 行），它从 Authorization: Bearer ... 头里解析 JWT，返回 AdminTokenPayload。解析失败抛 TokenInvalidError，FastAPI 转成 401。你排障看到 401，问题在这条依赖链上，不在 submit_chat 里。

_tenant: TenantContextDep 是租户上下文依赖（http_server/tenant_deps.py 第 75 行）。它从 JWT 的 tenant_id 出发，激活 PostgreSQL 的 search_path——这样后面的 DB 查询自动落到对的租户 schema。变量名带下划线 _tenant 表示「我不用它的值，但我需要它的副作用」。看到 400「缺少 tenant_id」，是这条依赖在报，不是业务代码。

关键模式

这个项目里几乎每个路由都挂 AuthDep + TenantContextDep。它们是横切关注点——鉴权和租户隔离不在业务函数里手写，而是靠 FastAPI 依赖注入在进函数体之前就搞定。排障时：4xx 状态码先归因到哪条依赖，再看业务逻辑。

幂等层

注意 run_idempotent_http 这一层。如果请求带了 idempotency_key，重复提交（双击、网络重试）会返回首次结果，不重复起会话；首次还在跑时重复请求返回 409。不带 key 则不去重，行为与旧链路一致。

如果用户反馈「点了一下发了两条」，先确认前端有没有传 idempotency_key。没传的话后端不会去重——这不是 bug，是契约。

真正干活的是 _do_submit

第 165 行的 _do_submit 调 get_chat_service().submit(...)，后者（services/chat_service.py）其实就是 chat(stream=False, _await_agent=False) 的别名——detached 执行：起一个后台任务跑 Agent，立即返回 session_id。Agent 跑的过程中往事件流里写事件，Phase 2 来订阅。

Phase 2 的代码骨架

主源：zeno-backend-agent/http_server/routers/chat.py · 第 200–223 行
@router.get("/{session_id}/progress", response_model=None)
async def stream_chat_progress(
    session_id: str,
    _auth: AuthDep,
    _tenant: TenantContextDep,
    last_event_id: Annotated[str | None, Header(alias="Last-Event-ID")] = None,
    after_seq: int | None = None,
):
    resume_from = _parse_after_seq(last_event_id, after_seq)
    svc = get_chat_service()

    async def _events():
        try:
            async for envelope in svc.subscribe(session_id, after_seq=resume_from):
                yield envelope
        except SessionNotFoundError:
            yield _session_not_found_envelope(session_id)

    return wire_streaming_response(_events())

几个要点：

  • last_event_id 用 Header(alias="Last-Event-ID") 从请求头取——浏览器 EventSource 断线重连时会自动带这个头。after_seq 是显式查询参数兜底。两者都走 _parse_after_seq 归一成「从第几条事件开始重放」。
  • svc.subscribe() 返回一个 AsyncIterator[dict]——注意它 yield 的是 wire 信封 dict，不是 SSE 字符串。SSE 帧的渲染在 wire_streaming_response 里做。
  • SessionNotFoundError 不抛 HTTP 异常，而是 yield 一条 system_error 事件收尾——这样 EventSource 和 fetch 客户端都能读到「会话不存在」，而不是看到一个连接错误。

SSE 帧渲染是共享的

wire_streaming_response 在 http_server/sse_wire.py。这个文件是全后端五条流共用的：chat 浏览器面、开放平台对话、workflow 画布、skill copilot、mcp playground——同一个 wire 信封 JSON，只在外层包一层 SSE 行。

主源：zeno-backend-agent/http_server/sse_wire.py · 第 41–54 行
def format_wire_sse(envelope: dict[str, Any]) -> str:
    wire_type = str(envelope.get("type", "message"))
    lines: list[str] = []

    seq = envelope.get("seq")
    if seq is not None:
        lines.append(f"id: {seq}")
    elif envelope.get("event_uuid"):
        lines.append(f"id: {envelope['event_uuid']}")

    lines.append(f"event: {sse_event_name(wire_type)}")
    lines.append(f"data: {json.dumps(envelope, ensure_ascii=False)}")
    return "\n".join(lines) + "\n\n"

信封结构：{type, session_id, seq, data, _meta}。seq 就是 id: 行的值，驱动 Last-Event-ID 重连。event: 行是 wire type 经 sse_event_name 映射后的名字（心跳呈现为 heartbeat）。data: 是整个信封 JSON。

排障 SSE 问题时，先在浏览器 DevTools 的 Network 面板看 event: 行的类型——它对应 EVENT-CATALOG.md 里的事件类型。知道类型就能反查是 core 哪个模块产出的。

检索检查

下面这道题测的是「你能不能把故障归因到对的层」。排障的核心技能不是记住每个函数，而是看到症状能快速锁定层。

排障检索

用户反馈「点发送后页面一直转圈，但控制台没有任何 4xx/5xx」。最该先查哪一层？

  • Phase 2 的 SSE 流——subscribe() 没把历史事件重放出来
  • Phase 1 的 submit()——请求可能根本没成功返回 session_id
  • AgentLoop——Agent 卡在工具调用里没产出事件
  • SSE 帧渲染——format_wire_sse 把信封序列化坏了

提示：「一直转圈 + 没有 4xx/5xx」说明前端在等一个永远不会来的响应。如果 Phase 1 成功返回了 session_id，前端就该去开 Phase 2 的 SSE 连接了——而 SSE 连不上通常会在 Network 面板显示出来。所以最可能是 Phase 1 请求挂住了（比如 run_idempotent_http 在等一个不回来的锁，或 chat_service.submit() 抛了没被 FastAPI 捕获的异常导致连接静默断开）。先看后端日志里有没有这次请求的「对话请求」日志行（chat_service.py 第 2531 行），确认请求到底进没进 service。
