上一课的 AgentLoop 第 ④ 阶段调 _execute_tools → tool_executor.execute_tools，拿到一个 dict[str, ToolExecutionResult]。这一课我们钻进 core/tool/，看这个 dict 是怎么来的——工具怎么被找到、怎么被校验、怎么并行跑、is_error 是谁判的。这是「工具没调」「工具报错」「工具被拦」类故障的落点。

三层结构：ToolExecutor（执行+校验+策略）→ ToolProviderManager（按优先级路由到 provider）→ ToolProviderController（每种工具类型的实际执行器）。Executor 负责「该不该跑、怎么跑」，Manager 负责「找谁跑」，Provider 负责「真跑」。

五种 Provider——工具从哪来

core/tool/provider_manager.py · PROVIDER_ORDER 第 30 行
PROVIDER_ORDER = [
    BUILTIN,        # 平台内置工具（最高优先级）
    API,            # 租户自建 HTTP API 工具（Webhook / OpenAPI）
    PYTHON,         # 租户自建 Python 工具
    TOOL_TEMPLATE,  # 卡片 DSL 工具（后端进程内产出卡片载荷）
    MCP,            # MCP 协议工具（外部 server）
    FRONTEND,       # 前端动态注册的 UI 交互工具（最低优先级）
]

同名工具冲突时，排在前面的 provider 优先——内置 > API > Python > 卡片 > MCP > 前端。这意味着如果你排障「自定义工具被内置工具盖掉了」，查这个名字是不是和内置工具重名。get_tool（provider_manager.py:79）会先 resolve_canonical_tool_name 把 LLM 返回的 function name 映射到内部 runtime 名，再按优先级找。

「模型调了工具但行为不对」时，先确认它调的是哪个 provider 的同名工具——get_tool 返回的 (descriptor, provider) 里 descriptor.provider_type 就是答案。别假设名字对就是对。

execute_tools：批量执行的三道关

core/tool/executor.py · execute_tools 第 772 行

AgentLoop 调的就是这个方法。它过三道关：

关 1：schema 预检（prevalidate_tool_calls）

prevalidation = self.prevalidate_tool_calls(tool_calls, ctx)   executor.py:787
if not prevalidation.get("passed", True):
    return self._schema_validator._schema_blocked_results(tool_calls, prevalidation)

整批工具的 schema 一次性预检。不通过 → 整批都不跑，直接返回每个工具一个 is_error=True 的 blocked 结果。这是「模型传的参数结构就不对」的落点——工具根本没被执行，不是执行后报错。

关 2：策略分组（_partition_by_policy）

groups = self._policy_enforcer._partition_by_policy(normalized_calls)  executor.py:814

把工具按策略分进若干 group。同 group 内可以并行（如果都允许），不同 group 串行。单个工具的 group 直接跑。这一步决定了「哪些工具能同时跑」。

关 3：并行执行 + sibling abort

if parallel_calls:
    tracked_results = await self._run_parallel_with_abort(parallel_calls, _run_one, max_parallel)
if serial_calls:
    for call in serial_calls:
        if abort:  # 上一个关键工具失败了 → 跳过剩余
            → 返回 is_error=True, error_msg="sibling_abort"
        tracked = await _run_one(call)
        if tracked.is_error and self._is_critical_tool(tracked.tool_name):
            abort = True

并行组用 asyncio.gather + Semaphore(max_parallel) 跑。串行组（is_concurrency_safe=False 的工具）一个个跑。关键工具（sandbox / code_interpreter / bash / shell，executor.py:865）失败会触发 sibling abort——同批次剩余工具直接跳过，返回 error_msg="sibling_abort"。

「模型调了 3 个工具，只跑了 1 个，另外 2 个显示 sibling_abort」——这是设计行为，不是 bug。查那个先跑的关键工具为什么 is_error=True。非关键工具失败不会触发 sibling abort。

🔴 is_error 是怎么判的——最该记住的一段

core/tool/executor.py · _execute_single_tracked 第 677-685 行
is_error = False
if isinstance(result, dict):
    error_value = result.get("error")
    is_error = (
        result.get("is_error") is True
        or result.get("success") is False
        or error_value not in (None, "", [], {})
    )

这是 ToolExecutionResult.is_error 的判定逻辑——三个条件取或：

  1. result["is_error"] is True——工具自己显式标了错
  2. result["success"] is False——工具用 success 字段标了失败
  3. result["error"] 非空（不是 None/空串/空列表/空 dict）——有 error 字段就算

注意第 3 条：只要 result 里有非空的 error 键就算失败，不管 success 是不是 True。所以工具返回 {"success": True, "error": "some warning"} 也会被判成 is_error=True。排障「工具明明成功了但 AgentLoop 当失败处理」时，查 result 里有没有意外的 error 字段。

和上一课的连接

AgentLoop 第 ④ 阶段只看 tracked.is_error（loop.py:674）来决定 has_tool_errors，但不因此终止循环——错误结果照常追加进消息历史给模型看。所以 is_error=True 的工具结果会变成一段 {"type":"tool_result","is_error":true,"content":"..."} 喂回模型，模型自己决定要不要重试。这条链路从 executor.py:681 的判定开始。

execute() 单工具的五道门

core/tool/executor.py · execute 第 463 行

每个工具走 execute()，过五道门才真正跑到 manager.invoke：

门 1: manager.get_tool(tool_name) is None?
       → 是：返回 TOOL_NOT_FOUND（is_error，不抛异常）        executor.py:487

门 2: manager.is_runtime_executable(tool_name) is False?
       → 是：返回 runtime_tool_view_reject（工具在当前视图不可执行）executor.py:500

门 3: _maybe_suspend_for_blocking（确认门 / 挂起）
       → 工具声明 blocking=USER_CONFIRM 时停下等人确认
       → 被拒/取消/超时 → 返回结构化失败（不抛异常！）       executor.py:337
       → AG-UI 下结构性恒关；开关 confirm_gate_enabled() 控制

门 4: _schema_validator._pre_execute_validation
       → schema 校验失败 → 返回 gate_error（is_error）        executor.py:514

门 5: manager.invoke(tool_name, input, ctx)
       → 真正调 provider.invoke 跑工具
       → 抛异常 → tool_error_result 包装成结构化失败返回       executor.py:534
       → 成功 → _postprocess_result_with_schema（压缩/校验输出）

关键点：前四道门失败都返回结构化 dict（is_error），不抛异常。只有第五道门 manager.invoke 抛异常时，才被 except 捕获包装成 tool_error_result。所以对 AgentLoop 来说，_execute_tools 几乎不会抛异常——除非 tool_executor 本身没配置（loop.py:1432 的 ValueError）。

这解释了上一课的「单工具 is_error 不终止循环」：execute() 把所有失败都包装成结构化 dict 返回，_execute_single_tracked 再包装成 ToolExecutionResult(is_error=True)。AgentLoop 看到的是「有错误的结果」而不是「异常」，所以照常追加进消息历史。只有 _execute_tools 自己抛异常（极罕见）才走 loop.py:698 的 except 分支终止。

确认门（confirm gate）：一个容易误判的挂起

core/tool/executor.py · _maybe_suspend_for_blocking 第 337 行

工具可以在 ToolSpec.execution.blocking 声明 USER_CONFIRM——执行前要人确认。这时 executor 会创建一个挂起项，停住等人确认（manager.wait，executor.py:419）。

三种结局，全部返回结构化失败，不抛异常：

  • 超时（TimeoutError）→ error_code=TIMEOUT，提示「未收到确认，不要重试」
  • 用户取消（CancelledError + 挂起项状态为 CANCELLED）→ error_code=POLICY_DENIED，提示「用户取消，不要重试」
  • 用户拒绝（其他异常）→ error_code=POLICY_DENIED，提示「用户拒绝，不要重试」

注释（executor.py:350）写得很直白：曾经这些会向上裸抛，穿透 execute_tools → loop._execute_tool_batch（那里 except: raise）→ 整轮 run 炸、模型什么都收不到。现在改成结构化失败，让模型知道「用户拒绝了，别重试」而不是让对话崩掉。

「AI 调了个工具然后整轮对话崩了、模型没收到任何结果」——如果你在旧版本上，查是不是确认门抛了没被捕获的异常。新版本已修。但如果你看到「工具显示被拒但 AI 还在重试同一个工具」，查模型有没有读懂 error_code=POLICY_DENIED 的「不要重试」提示——这是模型行为问题，不是工具层问题。

检索检验

排障检验

模型同时调了 3 个工具：search、bash、format。bash 执行后返回 is_error=True，search 和 format 显示 sibling_abort 没跑。AgentLoop 没有终止循环，模型收到了 bash 的错误结果和另外两个的 sibling_abort。这是 bug 吗？该查什么？

  • 是 bug，sibling_abort 不该跳过后续工具，查 _partition_by_policy
  • 是 bug，bash 失败应该终止整个 AgentLoop，查 loop.py 的 except 分支
  • 不是 bug，bash 是关键工具，失败触发 sibling abort 是设计行为；该查 bash 为何 is_error
  • 不是 bug，但该查 search 和 format 的 schema 为什么没过预检

bash 在 _CRITICAL_TOOLS（executor.py:865）里。关键工具 is_error=True 会触发 sibling abort（executor.py:856-857 / 897-899），同批次剩余工具被跳过并标 sibling_abort——这是设计行为，不是 bug。AgentLoop 不终止循环也是设计：单工具 is_error 不终止（上一课讲过），错误结果照常回传模型。该查的是 bash 为什么 is_error=True——看 bash 返回的 result dict 里 is_error/success/error 哪个触发了 executor.py:681 的判定。schema 预检不过会整批都不跑（包括 bash），和「bash 跑了」矛盾。
