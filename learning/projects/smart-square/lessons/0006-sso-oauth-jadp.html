第 6 课 · SSO 登录链路与 JADP/OAuth2/OIDC

课程 · ← 上一节：网关鉴权与 JWT · 全景图 · 学习使命

目标：理解用户从浏览器到拿到 JWT 的完整登录流程—— SSO ticket 换 token 的四步编排、JADP 是什么、/chat/ 路径的 Host SSO 认证、 OAuth2/OIDC 第三方登录。学完后你能画出整个登录时序图。

一、登录发生在哪里——网关承接了换取职责

上一课讲了网关怎么校验已有的 token。但 token 是怎么来的？答案是：登录换取。

本项目的登录换取逻辑在网关侧（SsoLoginController + SsoLoginService）， 而不是 admin。注释写明：「网关承接原 admin 的换取职责，knowledge 等前端登录不再依赖 admin 在线」。

这意味着即使 admin 宕机，用户仍然能登录——因为登录链路只依赖 gateway + sso + Redis，不依赖 admin。 这是可用性驱动的架构决策。

二、SSO 登录完整时序——ticket 换 token

这是平台用户（管理端/知识平台前端）登录的核心链路。用真实代码追踪：

三、四步编排——SsoLoginService 逐行拆解

// SsoLoginService.java
public Mono<TokenResult> login(String clientId, String ticket) {
    // 步骤 1：校验入参
    if (StrUtil.isBlank(ticket)) {
        return Mono.error(new SsoLoginException(401, "UNAUTHORIZED", "缺少 ticket"));
    }

    // 步骤 2：解析客户端凭证
    String resolvedClientId = StrUtil.isBlank(clientId)
            ? properties.getSsoLogin().getDefaultClientId()  //用 "square"
            : clientId;
    String clientSecret = properties.getSsoLogin().getClients().get(resolvedClientId);
    if (StrUtil.isBlank(clientSecret)) {
        return Mono.error(new SsoLoginException(401, "UNAUTHORIZED", "未注册的客户端"));
    }

    // 步骤 3+4：调 SSO 校验 ticket → 写 Redis 会话 → 签发 JWT
    return ssoValidateClient.validate(ticket, resolvedClientId, clientSecret)
            .flatMap(identity -> sessionWriter.write(identity)
                    .map(sessionId -> new TokenResult(
                            jwtSigner.sign(sessionId, identity.userId(),
                                    identity.orgCode(), identity.globalSessionId()),
                            expiresIn)));
}
四步编排：校验入参 → 解析客户端凭证 → SSO 校验 ticket → 写会话 + 签 JWT。 这是典型的编排模式（Orchestration）——一个 Service 方法串联多个步骤，每步的输出是下步的输入。

客户端凭证注册表

# gateway application-dev.yml
gateway:
  auth:
    sso-login:
      clients:
        square: ${SQUARE_CLIENT_SECRET:square-dev-secret}       # 广场前端
        knowledge: ${KNOWLEDGE_CLIENT_SECRET:knowledge-dev-secret}  # 知识平台前端
      default-client-id: square
为什么要 clientId/clientSecret：多个前端（广场、知识平台）共用同一个 SSO 登录链路， 但它们是不同的「客户端」（Relying Party，RP），各有自己的 secret。 SSO 校验 ticket 时会检查这个 clientId 是否有权访问，实现按客户端的准入控制。

不传 clientId 时默认用 square——兼容广场前端不传 clientId 的旧逻辑。

四、SSO 校验——SsoValidateClient

// SsoValidateClient.java
public Mono<SsoIdentity> validate(String ticket, String clientId, String clientSecret) {
    return webClient.post()
            .uri(properties.getSsoLogin().getValidateUrl())  // http://smart-square-sso/sso/validate
            .bodyValue(Map.of("ticket", ticket, "clientId", clientId, "clientSecret", clientSecret))
            .retrieve()
            .onStatus(status -> status == HttpStatus.UNAUTHORIZED,
                response -> Mono.error(new SsoLoginException(401, "UNAUTHORIZED", "ticket 无效或已过期")))
            .onStatus(status -> status == HttpStatus.FORBIDDEN,
                response -> Mono.error(new SsoLoginException(403, "FORBIDDEN", "当前账号无该系统访问权限")))
            .bodyToMono(String.class)
            .map(this::toIdentity);
}
三种错误状态的语义：
  • 401 UNAUTHORIZED：ticket 无效或已过期——ticket 是一次性的，用过就失效
  • 403 FORBIDDEN：ticket 有效但用户无权访问这个系统——准入拒绝，不是认证失败
  • 其他错误：认证中心不可用——统一回 401 让用户重试
注意 401 和 403 的区别：401 是「你没登录成功」，403 是「你登录了但没权限用这个系统」。
validate-url 用的是 lb 服务名：http://smart-square-sso/sso/validate—— 通过 Nacos 服务发现找到 sso 微服务。这就是上一课讲的 lb:// 机制在代码里的体现。

五、写 Redis 会话——SessionWriter

// SessionWriter.java
public Mono<String> write(SsoIdentity identity) {
    String sessionId = IdUtil.fastSimpleUUID();  // UUID 无连字符
    JSONObject payload = new JSONObject()
            .set("userId", identity.userId())
            .set("userName", identity.userName())
            .set("orgCode", identity.orgCode())
            .set("roles", identity.roles())
            .set("roleNames", identity.roleNames())
            .set("globalSessionId", identity.globalSessionId())
            .set("loginAt", now)
            .set("expireAt", now + ttl.toMillis());

    // 写会话主体
    redisTemplate.opsForValue().set("square:session:" + sessionId, payload.toString(), ttl);

    // 写反向索引（Set）
    if (StrUtil.isNotBlank(identity.globalSessionId())) {
        redisTemplate.opsForSet().add("square:gsid:" + identity.globalSessionId(), sessionId);
        redisTemplate.expire("square:gsid:" + identity.globalSessionId(), ttl);
    }
    return ...thenReturn(sessionId);
}
反向索引为什么用 Set 而不是 String： 一次 SSO 登录可以被多个 RP（广场、知识平台）各自换取本地会话， 全部挂在同一个 globalSessionId 下。如果用 String，后登录的会覆盖先登录的， 导致 back-channel 登出只删掉最后一个，其余成为孤儿会话。 用 Set 把所有 sessionId 都存下来，登出时整组删除。
globalSessionId 是 SSO 全局会话 ID——SSO 认证中心签发的， 代表「这一次 SSO 登录」。平台的 sessionId 是本地的，代表「这一次 ticket 换 token」。 一个 globalSessionId 可对应多个平台 sessionId（多 RP 共享一次 SSO 登录）。

back-channel 登出：SSO 通知所有 RP「这个全局会话登出了」， 各 RP 用 globalSessionId 查反向索引，删掉关联的所有本地会话——这就是单点登出。

六、签发 JWT——JwtSigner

// JwtSigner.java
public String sign(String sessionId, String userId, String orgCode, String globalSessionId) {
    Map<String, String> claims = MapUtil.<String, String>builder()
            .put("userType", "USER")
            .put("userId", userId)
            .put("sessionId", sessionId)       // ← 核心声明
            .build();
    if (StrUtil.isNotBlank(orgCode)) claims.put("orgCode", orgCode);
    if (StrUtil.isNotBlank(globalSessionId)) claims.put("globalSessionId", globalSessionId);

    return JWT.create()
            .addPayloads(claims)
            .setIssuedAt(new Date(now))
            .setExpiresAt(new Date(now + jwtExpiration.toMillis()))
            .setSigner(JWTSignerUtil.hs256(secret.getBytes(UTF_8)))
            .sign();
}
JWT 的 claims 结构：
  • sessionId——Redis 会话指针，验签后用它查 Redis 拿身份（上一课讲过）
  • userId / orgCode——冗余存一份，方便日志和调试
  • globalSessionId——登出时据此发起 SSO 全局登出，不依赖本地会话是否还在
  • userType=USER——平台用户类型固定为 USER
签发和验签用同一个 secret（gateway.auth.jwt-secret），天然对齐。

七、/chat/ 路径的 Host SSO——另一条认证路径

上一课提到 AuthGlobalFilter.resolveUser 对 /chat/** 走的是不同路径：

// AuthGlobalFilter.java
Mono<AuthenticatedUser> resolveUser(String path, String token) {
    if (path.startsWith(CHAT_PATH_PREFIX)) {
        return ssoUserResolver.resolve(token);  // /chat/ 只走 Host SSO / JADP
    }
    return sessionAuthenticator.authenticate(token)  // 其他路径先走平台 Session JWT
            .onErrorResume(e -> ssoUserResolver.resolve(token));  // 失败回退 JADP
}
为什么 /chat/ 和 admin 走不同认证路径： /chat/** 是 AI 助手对话，用户可能来自宿主系统（如企业内部平台）， 持有的是宿主的 JADP token，不是广场自己签发的 JWT。 所以 chat 路径直接走 JADP 解析，不走平台 Session JWT。

admin 路径的用户是广场自己登录的，持有平台 JWT，所以先走 Session JWT，失败再回退 JADP （可能是宿主系统嵌入广场管理端的情况）。

JADP 是什么

JADP = 企业内部的统一身份认证平台（类似企业版 OAuth2/OIDC）。 宿主系统通过 JADP 登录后拿到 access-token， 嵌入广场 AI 助手时把这个 token 带过来，广场用它向 JADP 拉取用户 profile。

SsoUserResolver 有两种模式：
  • mock 模式：开发联调用，token 格式 mock-jadp-access-token-{username}，按 token 里的用户名解析
  • jwt 模式：生产用，直连 JADP 代理 /api/jadp-proxy/current-user/profile 拉取真实身份
解析结果缓存在 Redis（键为 token 的 SHA-256 摘要，不落原始凭证），TTL 内不回源。

八、OAuth2/OIDC——开发者的第三方登录

前面讲的 SSO 是平台用户（管理员、知识平台用户）的登录。 但开发者（注册产品、管理 API 的用户）还有另一条登录路径——OAuth2/OIDC 第三方登录。

// OAuth2Controller.java（admin 模块）
@PostMapping("/developers/oauth2/token")
public AuthResult authenticate(
        @RequestParam("grant_type") String grantType,
        @RequestParam("assertion") String assertion) {
    return oAuth2Service.authenticate(grantType, assertion);
}
OAuth2 的 grant_type=assertion 模式：开发者用第三方 IdP（如 GitHub、Google） 签发的 assertion（通常是 ID Token）换取广场的 token。 这是 OAuth2 Token Exchange 模式——用外部凭证换本地凭证。

OIDC（OpenID Connect）是 OAuth2 之上的身份层协议， OidcController 提供 /developers/oidc/authorize 和 /developers/oidc/callback—— 标准的 OIDC 授权码流程。
