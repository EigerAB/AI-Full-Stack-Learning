第 5 课 · 网关集中鉴权与 JWT 机制

课程 · ← 上一节：Nacos 注册发现 · 全景图 · 学习使命

目标：理解一个请求从浏览器到 admin 的完整认证链路—— 网关怎么校验 JWT、怎么注入可信头、下游怎么还原身份、角色注解怎么拦截。 这是认证授权体系的第一节课，聚焦「认证」（你是谁），下一节课讲「授权」（你能做什么）。

一、认证 vs 授权——先分清两个概念

认证 (Authentication)授权 (Authorization)
回答什么问题你是谁？你能做什么？
本项目在哪做网关 AuthGlobalFilter + 下游 TrustedHeaderAuthenticationFilter下游 SecurityConfig + @AdminAuth 等注解
关键机制JWT 校验 + Redis 会话回查Spring Security 方法级安全 + 角色注解
本节课讲认证（网关侧），下一节课讲授权（下游侧）。 两节课合起来就是完整的「网关集中认证 + 下游分散授权」架构。

三、网关 AuthGlobalFilter——逐段拆解

步骤 1：剥离外部伪造头（防伪造的第一道防线）

// AuthGlobalFilter.java
ServerHttpRequest.Builder builder = request.mutate();
GatewayHeaders.ALL.forEach(header -> builder.headers(headers -> headers.remove(header)));
builder.header(GatewayHeaders.TRACE_ID, "trace-" + IdUtil.fastSimpleUUID());
为什么必须先剥离：如果外部请求自带 X-User-Id: admin 头， 网关不剥就直接转发，下游会以为这是管理员——身份伪造！ 所以网关在一切处理之前，先删除所有 X-User-* 头，再由自己重新注入校验过的真实身份。

安全前提：下游服务不可绕过网关直达。如果外部能直接访问 admin 的 8090 端口， 这层防护就失效了——所以部署时必须用网络策略隔离内部端口。

步骤 2：登录前置端点直接放行

if (path.startsWith(SSO_PATH_PREFIX) || path.startsWith(AUTH_PATH_PREFIX)) {
    return chain.filter(exchange.mutate().request(builder.build()).build());
}
/sso/**（SSO 登录链路）和 /auth/**（登录模式探测、ticket 换 token、登出） 必须在未登录时可达——否则逻辑死结：登出后 Cookie 还在，网关据此回 401， 前端跳登录页又要查登录模式 → 又 401 → 死循环。

放行≠免鉴权：网关只是不校验 token、不注入身份头，下游仍按匿名处理。

步骤 3：提取 token

String token = extractToken(request, path);
if (StrUtil.isBlank(token)) {
    return chain.filter(exchange.mutate().request(builder.build()).build());  // 无 token 放行
}
无 token 放行是刻意设计：有些端点是公开的（@PublicAccess）， 不需要登录。网关不知道哪些端点公开，所以无 token 时不拦截，交给下游 SecurityConfig 判断—— 公开端点放行，受保护端点返回 401。这就是「网关做认证，下游做授权」的分工。

步骤 4：JWT 校验 + Redis 会话回查

这是认证的核心。分两步：先验 JWT 签名，再查 Redis 会话。

4a. JwtVerifier——验签并提取 sessionId

// JwtVerifier.java
public String verifyAndGetSessionId(String token) {
    String secret = properties.getJwtSecret();       // HS256 密钥
    JWT jwt = JWTUtil.parseToken(token);
    boolean valid = jwt.setSigner(JWTSignerUtil.hs256(secret.getBytes(UTF_8))).verify();
    if (!valid) throw new IllegalArgumentException("令牌签名无效");

    // 检查过期
    Object expObj = jwt.getPayloads().get(JWT.EXPIRES_AT);
    if (expObj != null && Long.parseLong(expObj.toString()) * 1000 <= System.currentTimeMillis())
        throw new IllegalArgumentException("令牌已过期");

    Object sid = jwt.getPayload("sessionId");
    if (sid == null) throw new IllegalArgumentException("令牌缺少 sessionId 声明");
    return sid.toString();
}
JWT 在这个项目里只携带 sessionId，不携带用户信息。 这和很多教程里「JWT 里放 userId/roles」的做法不同。为什么？

因为JWT 是无状态的，签发后无法撤销。如果用户登出了，但 JWT 还没过期， 拿着旧 JWT 仍然能访问——这就是为什么本项目用 Redis 会话：JWT 只是一个「会话指针」， 真正的身份信息存在 Redis 里，登出时删掉 Redis 会话，JWT 立即失效。

这叫 Session-in-Redis + JWT-as-pointer 模式，兼顾了 JWT 的无状态校验和会话的可撤销性。

4b. SessionAuthenticator——查 Redis 拿真实身份

// SessionAuthenticator.java
public Mono<AuthenticatedUser> authenticate(String token) {
    return Mono.fromCallable(() -> jwtVerifier.verifyAndGetSessionId(token))
            .subscribeOn(Schedulers.boundedElastic())
            .flatMap(sessionId ->
                    redisTemplate.opsForValue()
                            .get("square:session:" + sessionId)  // 查 Redis
                            .mapNotNull(this::toUser));          // 解析 JSON → AuthenticatedUser
}
Redis 里存的会话 JSON 结构大致是： 
{"userId":"xxx", "userName":"张三", "orgCode":"ORG001",
 "roles":["47DB3A..."], "roleNames":["应用广场超级管理员"]}
square:session:{sessionId} 是 Redis key 的约定格式。 会话不存在（被登出删除或过期）时返回 Mono.empty()——网关据此回 401。

步骤 5：校验通过注入可信头 / 失败回 401

// 校验通过
return userMono.doOnNext(user -> injectHeaders(builder, user))
        .then(Mono.defer(() -> chain.filter(exchange.mutate().request(builder.build()).build())))
        .onErrorResume(e -> unauthorized(exchange, path, e));

// 注入头
private void injectHeaders(ServerHttpRequest.Builder builder, AuthenticatedUser user) {
    builder.header(GatewayHeaders.USER_ID, user.userId());
    builder.header(GatewayHeaders.USER_TYPE, user.userType());
    builder.header(GatewayHeaders.ORG_CODE, user.orgCode());
    builder.header(GatewayHeaders.USER_NAME, HeaderValueCodec.encode(user.userName()));  // 中文编码
    builder.header(GatewayHeaders.USER_ROLES, String.join(",", user.roles()));
    builder.header(GatewayHeaders.USER_ROLE_NAMES,
            HeaderValueCodec.encode(String.join(",", user.roleNames())));  // 角色名编码
}
带了 token 却确立不了身份 → 401，不降级放行。这是刻意的设计：

如果用户带了 token（自认为在登录态），但会话已被登出删除或过期， 网关必须回 401 让前端清理本地凭据并重新登录。如果静默降级放行， 前端永远等不到 401，会一直停在「看似登录、接口全返回空、写操作报权限不足」的残废状态。
中文编码：HTTP 头按 ISO-8859-1 传输，中文姓名和角色名（如「应用广场超级管理员」） 必须 URL 编码后写入头。下游 TrustedHeaderAuthenticationFilter 解码还原。 注意角色名先编码再 join——因为编码会把真实逗号转义为 %2C， 如果先 join 再编码，下游解码后切分会把单个角色名拆碎。

四、下游 TrustedHeaderAuthenticationFilter——还原身份

admin 收到网关转发的请求（带可信头，不带 token），用 TrustedHeaderAuthenticationFilter 还原身份：

// TrustedHeaderAuthenticationFilter.java（在 common 模块，admin/chat 共用）
@Override
protected void doFilterInternal(HttpServletRequest request, ...) {
    try {
        String traceId = request.getHeader(TrustedHeaders.TRACE_ID);
        if (StrUtil.isNotBlank(traceId)) {
            contextHolder.saveTraceId(traceId);
            MDC.put(MDC_TRACE_ID, traceId);  // 日志里能打 traceId
        }

        String userId = request.getHeader(TrustedHeaders.USER_ID);
        String userType = request.getHeader(TrustedHeaders.USER_TYPE);
        if (StrUtil.isNotBlank(userId) && StrUtil.isNotBlank(userType)) {
            String orgCode = request.getHeader(TrustedHeaders.ORG_CODE);
            String userName = decodeHeader(request.getHeader(TrustedHeaders.USER_NAME));
            List<String> roles = splitCsvHeader(request.getHeader(TrustedHeaders.USER_ROLES));
            List<String> roleNames = splitCsvHeader(
                    decodeHeader(request.getHeader(TrustedHeaders.USER_ROLE_NAMES)));

            // 构建 Spring Security Authentication
            String role = "ROLE_" + userType.toUpperCase();
            UsernamePasswordAuthenticationToken authentication =
                    new UsernamePasswordAuthenticationToken(userId, null,
                            Collections.singletonList(new SimpleGrantedAuthority(role)));
            authentication.setDetails(HostSsoUser.builder()
                    .userId(userId).userName(userName).orgCode(orgCode)
                    .roles(roles).roleNames(roleNames).traceId(traceId).build());

            SecurityContextHolder.getContext().setAuthentication(authentication);
            contextHolder.saveOrgCode(orgCode);
            contextHolder.saveRoles(roles);
            contextHolder.saveRoleNames(roleNames);
        }
        chain.doFilter(request, response);
    } finally {
        // 清理 ThreadLocal，避免线程复用导致身份泄漏
        contextHolder.clearOrgCode();
        contextHolder.clearRoles();
        contextHolder.clearRoleNames();
        contextHolder.clearTraceId();
        MDC.remove(MDC_TRACE_ID);
    }
}
三个关键设计：
  1. 不校验 token——网关已经校过了，下游只从头还原身份。注释明确写：「本过滤器不做 token 校验——校验已在网关集中完成」
  2. 写入两处：SecurityContextHolder（Spring Security 用）+ ContextHolder（业务代码用，ThreadLocal）。SSE 异步线程通过 Authentication details 回退获取
  3. finally 清理 ThreadLocal——Servlet 容器用线程池复用线程，不清理会导致下一个请求拿到上一个用户的身份（身份泄漏 bug）

五、SecurityConfig——下游的授权配置

// admin 的 SecurityConfig.java
@Configuration
@EnableMethodSecurity   // 开启方法级安全（@PreAuthorize 生效）
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(disable)                           // 无状态 API，不需要 CSRF
            .sessionManagement(STATELESS)            // 不创建 HttpSession，纯无状态
            .authorizeHttpRequests(auth -> {
                auth.dispatcherTypeMatchers(ASYNC).permitAll()  // SSE 异步分发放行
                    .requestMatchers(POST, "/developers").permitAll()  // 开发者注册公开
                    .requestMatchers(AUTH_WHITELIST).permitAll()       // 登录相关端点
                    .requestMatchers(SWAGGER_WHITELIST).permitAll()
                    .requestMatchers(OPEN_API_WHITELIST).permitAll();
                // @PublicAccess 注解的端点也放行（扫描器自动发现）
                for (PublicAccessEndpoint endpoint : publicEndpoints) {
                    auth.requestMatchers(endpoint.httpMethod(), endpoint.path()).permitAll();
                }
                auth.anyRequest().authenticated();   // 其余全部需要认证
            })
            .exceptionHandling(ex -> ex.authenticationEntryPoint(
                (req, res, authEx) -> {
                    res.setStatus(401);
                    res.getWriter().write("{\"code\":\"UNAUTHORIZED\",\"loginUrl\":\"...\"}");
                }))
            // 网关已校验 token，本服务仅从可信头还原身份
            .addFilterBefore(
                new TrustedHeaderAuthenticationFilter(contextHolder),
                UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}
三层放行策略：
  1. 硬编码白名单：登录端点、Swagger、系统端点——写在 AUTH_WHISTLIST 等数组里
  2. @PublicAccess 扫描：PublicAccessPathScanner 启动时扫描所有 Controller，找到标了 @PublicAccess 的方法，自动注册为公开端点——不用手动维护白名单
  3. 兜底：anyRequest().authenticated()——没明确放行的全部要认证

六、角色注解——@AdminAuth 的真面目

上一课你看到 ProductController 上标了 @AdminAuth。它的实现极其简洁：

// AdminAuth.java（在 common 模块）
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@PreAuthorize("isAuthenticated()")   // ← 就是这一行
public @interface AdminAuth {}
@AdminAuth 本质就是 @PreAuthorize("isAuthenticated()") 的别名。 @PreAuthorize 是 Spring Security 的方法级安全注解， isAuthenticated() 表示「只要登录了就放行」。

注释写的是「过渡期：登录即可访问；细粒度按组织/授权的鉴权改造见子系统 B」—— 说明当前 @AdminAuth 只做了认证级拦截（登录即可）， 更细粒度的授权（如「只有某组织的管理员才能删产品」）是后续改造方向。

其他注解同理：@DeveloperAuth、@AdminOrDeveloperAuth、@PublicAccess 都是 @PreAuthorize 的语义化别名，让 Controller 代码更易读。

七、为什么这样设计——架构决策回顾

决策选择核心原因
认证在哪做网关集中下游不用重复实现 JWT/JADP 校验，一处变更全局生效
JWT 携带什么只带 sessionIdJWT 不可撤销，身份放 Redis 会话里，登出删 Redis 即失效
身份怎么传给下游可信头 X-User-*头比 token 轻量，下游不用再解析 JWT，直接读头
防伪造网关先剥离再注入外部不能自带 X-User-* 头伪造身份
无 token 怎么办放行交下游网关不知道哪些端点公开，交给 SecurityConfig 判断
有 token 但失效401 不降级否则前端停在「看似登录实则失效」的残废状态
授权在哪做下游分散每个 Controller 用 @AdminAuth 等注解声明自己的权限要求
ThreadLocalfinally 清理线程池复用线程，不清理会身份泄漏

八、本课要点回顾

概念要点
认证 vs 授权认证=你是谁（网关做），授权=你能做什么（下游做）
AuthGlobalFilterOrder=-100 最先执行；剥离伪造头→放行登录端点→提取 token→校验→注入可信头
