第 2 课 · Spring Boot 基础锚定到 admin 模块

课程 · ← 上一节：技术栈全景 · 学习使命 · 资源

目标：通过 admin 模块的真实代码，理解 Spring Boot 的三个核心机制—— 自动配置、分层架构、统一响应。 学完后你能看懂一个请求从进来到出去经历了什么。

一、起点：启动类上的注解

打开 smart-square-admin/src/main/java/com/smartsquare/SmartSquareAdminApplication.java， 整个应用就从这里启动。一个类、六个注解、一行 main，但每个注解都在开启一整块能力：

@SpringBootApplication
@EnableScheduling
@EnableDiscoveryClient
@EnableFeignClients(basePackages = "com.smartsquare")
@EnableConfigurationProperties({AcpProperties.class})
@MapperScan("com.smartsquare.mapper")
public class SmartSquareAdminApplication {
    public static void main(String[] args) {
        SpringApplication.run(SmartSquareAdminApplication.class, args);
    }
}
1@SpringBootApplication——这是 Spring Boot 的「一键启动」。 它其实是三个注解的合体：@SpringBootConfiguration（标记配置类）+ @EnableAutoConfiguration（自动配置）+ @ComponentScan（组件扫描）。

自动配置是 Spring Boot 最核心的能力：你引入了 spring-boot-starter-web， 它就自动配好内嵌 Tomcat、DispatcherServlet、JSON 序列化；你引入了 mybatis-plus， 它就自动配好 SqlSessionFactory。你不用写一行 XML 配置。

组件扫描会扫描 com.smartsquare 包下所有带 @Controller、 @Service、@Component、@Configuration 的类，把它们注册成 Bean。 这就是为什么你只要给类加个 @Service 注解，就能在其他地方 @RequiredArgsConstructor 注入它。
2@EnableDiscoveryClient——开启服务注册发现，把自己注册到 Nacos， 让 gateway 能通过 Nacos 找到 admin。这是微服务架构的关键，下一阶段细讲。
3@EnableFeignClients——开启声明式 HTTP 客户端， 让 admin 能用接口调其他服务。本项目里 chat 微服务会用 Feign 调 admin。
4@MapperScan("com.smartsquare.mapper")——告诉 MyBatis-Plus 去哪个包扫描 Mapper 接口。Mapper 是数据访问层，等会儿在三层架构里会看到它。
5@EnableConfigurationProperties({AcpProperties.class})—— 把 application.yml 里 acp: 那段配置绑定到 AcpProperties Java 类。 这是 Spring Boot「配置即类型」的体现：yml 里的字符串变成有类型的 Java 对象，带 IDE 提示和校验。
关键认知：Spring Boot 的「魔法」不是魔法，是「约定优于配置」—— 你按它的约定放注解、放包结构，它就自动帮你配好基础设施。理解了这一点，看任何 Spring Boot 项目都不会慌。

二、配置文件：application.yml 的分层设计

Spring Boot 的配置是分环境的。看 admin 的 resources 目录：

application.yml        ← 入口，只选 profile
application-dev.yml     ← 开发环境
application-nwtest.yml  ← 内网测试
application-h2.yml      ← 内存库（本地调试）
application-local.yml   ← 个人覆盖（不入 Git，打包排除）

application.yml 只有一行有用的：

spring:
  profiles:
    active: ${SPRING_PROFILES_ACTIVE:dev}
${SPRING_PROFILES_ACTIVE:dev} 是 Spring 的占位符语法： ${环境变量名:默认值}。优先读环境变量 SPRING_PROFILES_ACTIVE， 没设就用默认值 dev。这样线上不用重新打包，改环境变量就能切配置。

真正的配置在 application-dev.yml 里。看几个关键段：

数据源——达梦数据库

spring:
  datasource:
    url: jdbc:dm://${db.host}:${db.port}/${db.name}
    driver-class-name: dm.jdbc.driver.DmDriver
db:
   host: ${DB_HOST:8.166.117.70}
   port: ${DB_PORT:5236}
   name: ${DB_NAME:SMARTSQUARE}
注意 jdbc:dm:// 和 dm.jdbc.driver.DmDriver—— 这是达梦数据库的 JDBC 协议和驱动，不是 MySQL 的 jdbc:mysql://。 ${db.host} 引用的是下面 db: 段定义的占位符，而 db.host 又用 ${DB_HOST:8.166.117.70} 读环境变量。两层占位符是常见模式： yml 内部用短名引用，短名再读环境变量，让配置既可读又可覆盖。

MyBatis-Plus 配置

mybatis-plus:
  type-handlers-package: com.smartsquare.typehandler
  configuration:
    map-underscore-to-camel-case: true
  global-config:
    db-config:
      id-type: auto
map-underscore-to-camel-case: true 让数据库的 product_name 自动映射到 Java 的 productName——数据库下划线命名和 Java 驼峰命名的转换不用手写。 id-type: auto 表示主键用数据库自增。

三、三层架构：一个请求的完整旅程

这是本课的核心。用 ProductController 的「创建产品」接口追踪一个请求：

浏览器 POST /products (JSON body) │ ▼ ┌─ Controller 层 ──────────────────────────────────┐ │ ProductController.createProduct(param) │ │ · @PostMapping("/products") 路由匹配 │ │ · @Valid 触发参数校验 │ │ · @AdminAuth 角色鉴权（AOP 切面） │ │ · 调用 productService.createProduct(param) │ │ · 直接 return ProductResult（不包装！） │ └──────────────────┬───────────────────────────────┘ ▼ ┌─ Service 层 ─────────────────────────────────────┐ │ ProductService.createProduct(param) │ │ · @Service @Slf4j @RequiredArgsConstructor │ │ · 事务边界在这里（@Transactional） │ │ · 业务逻辑：校验、转换、调用 Mapper │ │ · 抛 BusinessException 表示业务错误 │ └──────────────────┬───────────────────────────────┘ ▼ ┌─ Mapper 层（数据访问）─────────────────────────────┐ │ ProductMapper.insert(product) │ │ · MyBatis-Plus 的 BaseMapper 提供 CRUD │ │ · 实际执行 SQL，写入达梦数据库 │ └──────────────────┬───────────────────────────────┘ ▼ ┌─ Entity 层 ──────────────────────────────────────┐ │ Product (仅作持久化容器，不写业务逻辑) │ │ · @Data @Builder @NoArgsConstructor │ │ · 继承 BaseEntity │ │ · 字段对应数据库列 │ └──────────────────────────────────────────────────┘ │ ▼ (Controller 返回 ProductResult) ┌─ ResponseAdvice（统一响应）───────────────────────┐ │ 自动拦截所有 Controller 返回值 │ │ · 把 ProductResult 包成 Response │ │ · {"code":"SUCCESS","data":{...}} │ │ · Controller 不用手动包装！ │ └──────────────────────────────────────────────────┘

看真实代码——Controller

@Tag(name = "API产品管理", description = "...")
@RestController
@RequestMapping("/products")
@Slf4j
@RequiredArgsConstructor
public class ProductController {

    private final ProductService productService;  // 构造器注入，不用 @Autowired

    @Operation(summary = "创建API产品")
    @PostMapping
    @AdminAuth
    public ProductResult createProduct(@RequestBody @Valid CreateProductParam param) {
        return productService.createProduct(param);
    }
}
逐行拆解：
  • @RestController = @Controller + @ResponseBody，返回值自动转 JSON
  • @RequestMapping("/products") 类级别路由前缀，方法级别 @PostMapping 拼成 POST /products
  • @RequiredArgsConstructor（Lombok）自动生成构造器，private final 字段通过构造器注入——这是规范要求的注入方式，禁止用 @Autowired
  • @RequestBody 把 JSON body 反序列化成 CreateProductParam，@Valid 触发参数校验
  • @AdminAuth 是项目自定义注解，通过 AOP 切面校验调用者是否是管理员——下阶段认证课细讲
  • Controller 直接 return 业务对象，不手动包装——这是本项目的硬性规范

四、统一响应：ResponseAdvice 的魔法

Controller 明明返回的是 ProductResult，前端收到的却是 {"code":"SUCCESS","data":{...}}。谁包的？是 ResponseAdvice：

@RestControllerAdvice
public class ResponseAdvice implements ResponseBodyAdvice<Object> {

    // 判断要不要拦截这个返回值
    @Override
    public boolean supports(MethodParameter returnType, ...) {
        Class<?> type = returnType.getMethod().getReturnType();
        return !type.equals(ResponseEntity.class)
                && !type.equals(Response.class)        // 已经是 Response 就不重复包
                && !type.equals(SseEmitter.class)      // SSE 流式不包
                && !type.equals(Flux.class)            // 响应式流不包
                && !type.equals(Mono.class);
    }

    // 拦截后把返回值包成 Response
    @Override
    public Object beforeBodyWrite(Object body, ...) {
        if (body instanceof Response) return body;  // 避免重复包装
        response.setStatusCode(HttpStatus.OK);
        return Response.ok(body);   // → {"code":"SUCCESS","data":body}
    }
}
为什么这样设计：如果每个 Controller 方法都手动 return Response.ok(data)， 会有几百处重复代码，而且容易漏包或包错。用 ResponseBodyAdvice 在框架层统一拦截， Controller 只关心业务逻辑，返回业务对象即可。这是「关注点分离」的典型实践。

五、统一异常：ExceptionAdvice 的三道防线

业务出错了怎么办？本项目禁止用 null 表示业务错误，统一抛 BusinessException， 由 ExceptionAdvice 捕获并转成统一响应：

@RestControllerAdvice
public class ExceptionAdvice {

    // 防线 1：业务异常（如"产品不存在"）
    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<Response<Void>> handleBusinessException(BusinessException e, ...) {
        return ResponseEntity.status(e.getStatus())
                .body(Response.fail(e.getCode(), e.getMessage()));
    }

    // 防线 2：参数校验异常（如 @Valid 不通过）
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<Response<Void>> handleParamVerifyException(...) { ... }

    // 防线 3：兜底——所有未捕获的异常
    @ExceptionHandler(Exception.class)
    public ResponseEntity<Response<Void>> handleSystemException(Exception e, ...) {
        log.error("[System Exception] ...", e);  // 记完整堆栈
        return ResponseEntity.status(500)
                .body(Response.fail("INTERNAL_ERROR", ...));
    }
}
三层异常处理的分工：
  • BusinessException——预期内的业务错误（产品不存在、权限不足），记 warn 级别，不记堆栈
  • MethodArgumentNotValidException——用户提交的参数不合法，也是 warn，不记堆栈
  • Exception 兜底——意料之外的系统 bug，记 error 级别 + 完整堆栈，方便排查
日志级别区分是有意为之：业务错误和参数错误是用户行为，不该污染错误日志；只有系统异常才需要堆栈。

六、Response 的结构

@Data @Accessors(chain = true)
@NoArgsConstructor @AllArgsConstructor
public class Response<T> {
    private String code;     // "SUCCESS" 或错误码
    private String message;  // 错误信息（成功时为空）
    private T data;          // 业务数据

    public static <T> Response<T> ok(T data) {
        return new Response<T>().setCode("SUCCESS").setData(data);
    }
    public static <T> Response<T> fail(String code, String message) {
        return new Response<T>().setCode(code).setMessage(message);
    }
}
@Accessors(chain = true) 让 setter 返回 this，可以链式调用： new Response<T>().setCode("SUCCESS").setData(data)。 code 是字符串而不是数字——用 "SUCCESS" / "PRODUCT_NOT_FOUND" 这样的语义化错误码，比 200 / 404 更易读、更稳定。
