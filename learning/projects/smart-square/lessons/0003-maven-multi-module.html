第 3 课 · Maven 多模块与依赖方向

课程 · ← 上一节：Spring Boot 基础 · 全景图 · 学习使命

目标：理解 SmartSquare 为什么拆成七个 Maven 模块、依赖方向是怎么规定的、 父 POM 如何集中管控版本。学完后你能判断「一段代码应该放在哪个模块」。

一、为什么不用单体，要拆多模块

上一课你在 admin 里看到了 Controller → Service → Mapper 三层。如果整个项目只有 admin 一个模块， 那 chat 微服务想复用 Response、BusinessException、ContextHolder 怎么办？ 把 admin 整个引进来？那 chat 就被迫依赖了 admin 的全部 Controller、Service、Mapper—— 编译变慢、耦合变重、改 admin 一个字段的注释都可能让 chat 重新构建。

多模块拆分的本质：把「会被多处复用的东西」和「只属于某个服务的东西」分开。 共享的放 common/proto，服务私有的放各自的模块。依赖方向单向流动，避免循环引用。

二、七个模块与依赖方向

先看父 pom.xml 里声明的全部模块：

<modules>
    <module>smart-square-common</module>
    <module>smart-square-proto</module>
    <module>smart-square-admin</module>
    <module>smart-square-gateway</module>
    <module>smart-square-chat</module>
    <module>smart-square-sso</module>
    <module>smart-square-knowledge</module>
</modules>

它们的依赖方向是这样的（箭头表示「依赖谁」）：

┌─────────────────────────────────┐ │ smart-square (父 POM) │ │ 统一管控版本 + 插件版本 │ └──────────────┬──────────────────┘ │ (parent 继承) ┌────────────┬───────────┼───────────┬────────────┐ ▼ ▼ ▼ ▼ ▼ ┌──────────┐ ┌──────────┐ ┌────────┐ ┌──────────┐ ┌──────────┐ │ common │ │ proto │ │ admin │ │ gateway │ │ chat │ │ (公共库) │ │ (gRPC契约)│ │(主服务) │ │ (网关) │ │(对话微服) │ └────┬─────┘ └────┬─────┘ └───┬────┘ └──────────┘ └─────┬────┘ │ │ │ │ │ │ ┌─────┘ │ │ │ │ (依赖 common + proto) │ │ │ │ ┌────────────────────┘ │ │ │ │ (依赖 common + proto) │ │ ▼ ▼ │ │ ┌──────────────┐ │ │ │ common │ │ │ │ proto │ │ │ └──────────────┘ │ │ │ │ gateway 不依赖 common/proto │ │ （网关只做鉴权路由，不碰业务） │ │ ▼ ▼ common 和 proto 不依赖任何业务模块 （最底层，只依赖第三方库）
关键规则：依赖方向严格单向
  • common 和 proto 在最底层，不依赖任何业务模块
  • admin 和 chat 依赖 common + proto
  • gateway 独立——不依赖 common/proto，因为它不碰业务逻辑，只做鉴权和路由
  • admin 和 chat 之间不互相依赖——chat 要调 admin 走 OpenFeign（运行时 HTTP），不是 Maven 依赖（编译期）

三、逐个模块看 pom.xml

smart-square-common（公共基础设施）

放什么：Response、BusinessException、ErrorCode、ContextHolder、 鉴权注解（@AdminAuth 等）、领域事件定义、IdGenerator、CacheUtil、MyBatis 配置、MinIO 配置。

依赖：mybatis-plus-starter、spring-boot-starter-web、spring-boot-starter-security、hutool、caffeine、minio、reactor-core、lombok 不依赖：任何 smart-square-* 模块

为什么 common 依赖 web 和 security：因为 ResponseAdvice 用了 @RestControllerAdvice（web）， ContextHolder 用了 SecurityContext（security）。common 不是纯工具包，它承载了跨服务共享的框架级基础设施。

smart-square-proto（gRPC 契约）

放什么：.proto 文件。编译时由 protobuf-maven-plugin 自动生成 Java 的消息类和 gRPC stub。

依赖：grpc-stub、grpc-protobuf、protobuf-java 不依赖：任何 smart-square-* 模块

为什么单独成模块：admin 和 chat 都要调用意图识别 gRPC 服务，需要同一份 .proto 编译出的 stub。 如果 proto 定义放在 admin 里，chat 就得依赖 admin——违反依赖方向。单独成模块让两边引用同一份契约。

smart-square-admin（主服务）

放什么：32+ Controller、全部业务 Service、Entity、Mapper、Flyway 迁移脚本、智能编码、MCP 托管、启动入口。

依赖：smart-square-common（共享基础设施） 还依赖：mybatis-plus、DmJdbcDriver（达梦驱动）、springdoc、oauth2-client、easyexcel、aliyun SDK（APIG/MSE）、higress-admin-sdk、bouncycastle 等

admin 是最「重」的模块——承载了绝大部分业务逻辑。它的 pom 依赖列表最长，因为要对接各种第三方网关 SDK 和 AI 能力。

smart-square-chat（对话微服务）

放什么：ChatMessageController（SSE）、ChatOrchestrator（意图路由）、A2A 协议对接、独立 Entity/Mapper。

依赖：smart-square-common + smart-square-proto 还依赖：spring-cloud-starter-openfeign（调 admin）、grpc-netty-shaded（gRPC 调意图识别）、agentscope、dashscope、flyway、DmJdbcDriver

注意 chat 依赖 proto 而 admin 也依赖 proto——两端共享同一份 gRPC 契约，这正是 proto 独立成模块的价值。

smart-square-gateway（统一网关）

放什么：AuthGlobalFilter、SSO 登录、JWT 签发/校验、身份头注入。

依赖：spring-cloud-starter-gateway-server-webflux、nacos-discovery、loadbalancer、redis-reactive、hutool、lombok 不依赖：smart-square-common、smart-square-proto

为什么 gateway 不依赖 common：网关是 WebFlux 响应式模型，common 里的 ResponseAdvice、ContextHolder 是基于 WebMVC（阻塞式）的。如果 gateway 依赖 common，会引入不兼容的 WebMVC 依赖。网关的鉴权逻辑自己写，不复用 common 的安全设施。

四、父 POM 的集中管控

打开根目录 pom.xml，你会看到两个关键段：

properties——版本号集中声明

<properties>
    <spring-boot.version>3.5.9</spring-boot.version>
    <spring-cloud.version>2025.0.0</spring-cloud.version>
    <mybatisplus.version>3.5.9</mybatisplus.version>
    <dm8.jdbc.version>8.1.3.62</dm8.jdbc.version>
    <hutool.version>5.8.33</hutool.version>
    ...
</properties>

dependencyManagement——版本托管

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.baomidou</groupId>
            <artifactId>mybatis-plus-spring-boot3-starter</artifactId>
            <version>${mybatisplus.version}</version>
        </dependency>
        ...
    </dependencies>
</dependencyManagement>
dependencyManagement 和 dependencies 的区别——这是 Maven 最容易混淆的点：
  • <dependencies>：真正引入依赖，子模块自动继承
  • <dependencyManagement>：只声明版本，不引入。子模块要用还得在自己的 <dependencies> 里写，但不用写 <version>
举例：common 的 pom 里写 <artifactId>mybatis-plus-spring-boot3-starter</artifactId> 但没有 <version>—— 版本由父 POM 的 dependencyManagement 托管。这样升级版本只改父 POM 一处，所有模块同步。
项目规范（硬性）：
  • 第三方依赖版本必须在父 POM 的 <properties> + <dependencyManagement> 管理
  • 子模块 POM 引用已管理依赖时不写 <version>
  • 子模块 POM 里已有的直接版本声明属于技术债，不应继续复制
  • 新增依赖时：先更新父 POM，再在模块 POM 引用
违反这些规则会导致版本不一致——比如 admin 用 hutool 5.8.33，chat 用 5.8.20，API 行为差异引发难查的 bug。

五、pluginManagement——插件版本也集中管

同样的模式用于 Maven 插件：

<pluginManagement>
    <plugins>
        <plugin>
            <groupId>com.diffplug.spotless</groupId>
            <artifactId>spotless-maven-plugin</artifactId>
            <version>${spotless-maven-plugin.version}</version>
        </plugin>
        ...
    </plugins>
</pluginManagement>

Spotless（代码格式化）、protobuf-maven-plugin（proto 编译）、maven-compiler-plugin 等插件的版本 都在父 POM 统一管理。这保证了所有模块用同一套构建工具链。

六、实战判断：一段代码该放哪个模块

这是你在维护开发时最常遇到的决策。用几个真实例子练习：

要写的东西放哪个模块为什么
一个新的 REST Controller（如 OrderController）adminController 是服务私有逻辑，只有 admin 暴露 REST API
一个新的业务异常码（如 ORDER_NOT_FOUND）commonErrorCode 枚举在 common，chat 也可能抛这个码
一个新的 gRPC 消息定义proto.proto 契约要被 admin 和 chat 共享
一个新的网关鉴权过滤器gateway网关自己的逻辑，且 gateway 不依赖 common
一个新的领域事件（如 OrderDeletingEvent）common事件定义在 common 的 core/event/，供 admin 共享
一个新的 SSE 对话事件类型chatAG-UI 对话是 chat 专属逻辑，admin 不需要
一个新的 MyBatis TypeHandler看情况如果 admin 和 chat 都用→common；只有 chat 用→chat
判断口诀：
  1. 只有网关用→gateway（网关不依赖 common）
  2. admin 和 chat 都会用→common（共享基础设施）
  3. 是 gRPC 契约→proto（编译生成的 stub 要共享）
  4. 只有某个服务用→那个服务自己的模块

七、构建顺序的坑

多模块项目有构建顺序问题。从 local/AGENTS.md 的操作记录里可以看到真实踩坑经验：

真实坑：common 模块代码变更后，如果只 mvn package admin， admin 编译时可能从本地 .m2 仓库拿到旧版 common，找不到 common 的新方法。

正确做法：common 变更后先 mvn install common proto 把新版本装进 .m2， 再 mvn package admin。或者直接 mvn install -pl common,proto -am（-am 表示同时构建依赖）。

proto 模块也有类似问题：mvn clean 会删除 proto 的 protoc 依赖缓存，重新下载时可能失败。 所以构建时要注意顺序，必要时跳过 proto 的 clean。
