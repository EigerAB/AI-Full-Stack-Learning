第 7 课 · 角色注解与方法级授权

课程 · ← 上一节：SSO 登录链路 · 全景图 · 学习使命

目标：理解从网关注入身份头到Controller 方法上的 @AdminAuth 生效的完整链路—— 身份怎么还原、Spring Security 怎么配置、注解怎么拦截、角色怎么判定。 学完后你能回答「一个 @AdminAuth 注解的请求经历了哪些检查」。

一、回顾——我们已经走到哪里

前两课讲了认证授权体系的前半段：

  • 第 5 课：网关 AuthGlobalFilter 集中校验 token，注入 X-User-* 身份头
  • 第 6 课：用户怎么登录拿到 token（SSO ticket 换 JWT、JADP/OAuth2/OIDC）

但故事只讲了一半——网关注入了身份头之后呢？下游服务怎么拿到这个身份？Controller 上的 @AdminAuth 注解是谁在检查、怎么检查的？这一课就补完最后一段。

关键心智：网关负责认证（你是谁），下游负责授权（你能干什么）。 网关注入 X-User-* 头 → 下游还原身份 → Spring Security 方法级注解做权限判断。

三、下游身份还原——TrustedHeaderAuthenticationFilter

网关注入的 X-User-* 头是 HTTP 头，Spring Security 不认识它们。需要有人把头翻译成 Spring Security 能理解的 Authentication 对象——这就是 TrustedHeaderAuthenticationFilter 的职责。

// smart-square-common/.../security/TrustedHeaderAuthenticationFilter.java
@Override
protected void doFilterInternal(HttpServletRequest request,
                                HttpServletResponse response,
                                FilterChain chain) throws ServletException, IOException {
    // 1. 处理 traceId（独立于用户身份）
    String traceId = request.getHeader(TrustedHeaders.TRACE_ID);
    if (StrUtil.isNotBlank(traceId)) {
        contextHolder.saveTraceId(traceId);
        MDC.put(MDC_TRACE_ID, traceId);  // 日志链路追踪
    }

    // 2. 读取用户身份头
    String userId = request.getHeader(TrustedHeaders.USER_ID);
    String userType = request.getHeader(TrustedHeaders.USER_TYPE);
    if (StrUtil.isNotBlank(userId) && StrUtil.isNotBlank(userType)) {
        String orgCode = request.getHeader(TrustedHeaders.ORG_CODE);
        String userName = decodeHeader(request.getHeader(TrustedHeaders.USER_NAME));
        List roles = splitCsvHeader(request.getHeader(TrustedHeaders.USER_ROLES));
        List roleNames = splitCsvHeader(
            decodeHeader(request.getHeader(TrustedHeaders.USER_ROLE_NAMES)));

        // 3. 构建 Spring Security Authentication
        //    authority = ROLE_，如 ROLE_ADMIN
        String role = CommonConstants.ROLE_PREFIX + userType.toUpperCase(Locale.ROOT);
        UsernamePasswordAuthenticationToken authentication =
            new UsernamePasswordAuthenticationToken(
                userId,                          // principal
                null,                            // credentials（无密码）
                Collections.singletonList(
                    new SimpleGrantedAuthority(role)));  // authorities

        // 4. 将完整身份存入 details（供 SSE 异步线程回退用）
        authentication.setDetails(HostSsoUser.builder()
            .userId(userId)
            .userName(userName)
            .orgCode(orgCode)
            .roles(roles)
            .roleNames(roleNames)
            .traceId(traceId)
            .build());

        // 5. 存入 SecurityContextHolder（Spring Security 用）
        SecurityContextHolder.getContext().setAuthentication(authentication);

        // 6. 存入 ContextHolder ThreadLocal（业务代码用）
        contextHolder.saveOrgCode(orgCode);
        contextHolder.saveRoles(roles);
        contextHolder.saveRoleNames(roleNames);
    }

    chain.doFilter(request, response);

    // 7. 请求结束，清理 ThreadLocal（防止线程池复用导致身份串号）
    contextHolder.clearOrgCode();
    contextHolder.clearRoles();
    contextHolder.clearRoleNames();
    contextHolder.clearTraceId();
}
为什么存两个地方？ SecurityContextHolder 是 Spring Security 的标准上下文，@PreAuthorize 从这里读身份。 ContextHolder 是项目自己的 ThreadLocal，业务代码（如 Service 层）通过它拿 orgCode、roleNames 更方便。 两者存的是同一份身份，只是入口不同。

中文编码的坑

注意 decodeHeader 和 splitCsvHeader 的调用——HTTP 头只能传 ISO-8859-1，中文姓名（如「张三」）和含逗号的角色名列表需要特殊处理：

  • 网关注入时：URL 编码中文，逗号转义为 %2C
  • 下游还原时：先 URL 解码，再按逗号切分

如果不做这步，中文姓名会乱码，角色名列表会被逗号错误切分。

HostSsoUser——身份详情对象

// smart-square-common/.../security/HostSsoUser.java
@Data @Builder
public class HostSsoUser {
    private String userId;
    private String userName;
    private String orgCode;
    private List roles;       // JADP roleCode，仅作透传与留痕
    private List roleNames;   // JADP roleName，角色判定的唯一判据
    private String traceId;
}

这个对象存在 Authentication.details 里。为什么不用 principal？因为 principal 已经是 userId 字符串了，而 details 可以放任意对象，适合存完整身份快照。

四、ContextHolder——业务代码的身份入口

ContextHolder 是项目自己的鉴权上下文，用 ThreadLocal 存当前请求的身份信息。业务代码（Service 层）需要拿当前用户信息时，不用直接碰 Spring Security，而是通过 ContextHolder。

// smart-square-common/.../security/ContextHolder.java
public class ContextHolder {
    private final ThreadLocal orgContext = new ThreadLocal<>();
    private final ThreadLocal> rolesContext = new ThreadLocal<>();
    private final ThreadLocal> roleNamesContext = new ThreadLocal<>();
    private final ThreadLocal traceIdContext = new ThreadLocal<>();

    // 获取 orgCode——优先 ThreadLocal，回退 SecurityContext
    public String getOrgCode() {
        String orgCode = orgContext.get();
        if (StrUtil.isNotBlank(orgCode)) return orgCode;

        // 回退：从 Authentication.details 获取（SSE 异步线程场景）
        try {
            Authentication auth = SecurityContextHolder.getContext().getAuthentication();
            if (auth != null && auth.getDetails() instanceof HostSsoUser ssoUser) {
                return ssoUser.getOrgCode();
            }
        } catch (Exception ignored) {}
        return null;
    }

    // 角色判断
    public boolean isAdministrator() {
        return getCurrentUserType() == UserType.ADMIN;
    }

    public boolean isDeveloper() {
        return getCurrentUserType() == UserType.DEVELOPER;
    }

    // 超管判断——用 roleName 而非 roleCode
    public boolean isSuperAdmin() {
        List superRoles = permissionProperties.getSuperAdminRoles();
        if (superRoles == null || superRoles.isEmpty()) return false;
        return getRoleNames().stream().anyMatch(superRoles::contains);
    }
}
为什么 isSuperAdmin 用 roleName？ JADP 的 roleCode（roleId）是不可读随机串，如 47DB3AED9CE54400...， 没法写进配置文件。而 roleName 是可读角色名，如「应用广场超级管理员」。 所以 permission.super-admin-roles 配置的是角色名列表，判定时用 roleName 求交。

这是第 7 课（JADP 笔记）里讲的「角色判定一律用 roleName」在代码里的体现。

SSE 异步线程的回退机制

为什么 getOrgCode() 有个回退逻辑？因为 SSE 流式响应。

普通请求：一个线程从头跑到尾，ThreadLocal 全程有效。

SSE 请求：Controller 方法返回后，Spring MVC 用 ASYNC 派发继续推送事件，此时可能切换到另一个线程——ThreadLocal 丢了。

回退方案：身份快照存在 Authentication.details（HostSsoUser），SecurityContextHolder 在同一次请求里跨线程仍可访问（Spring Security 做了线程继承）。所以 ThreadLocal 为主、SecurityContext 为辅。

五、六个角色注解——从 @AdminAuth 到 @PublicAccess

项目定义了六个注解，全部在 smart-square-common/.../core/annotation/ 下。它们的本质是 组合了 @PreAuthorize 的元注解。

注解 @PreAuthorize 表达式 含义 用在哪
@AdminAuth isAuthenticated() 要求登录（过渡期，细粒度鉴权待改造） admin 管理端接口
@DeveloperAuth isAuthenticated() 要求登录（同上） 开发者门户接口
@AdminOrDeveloperAuth isAuthenticated() 要求登录（同上） 管理员和开发者都能用的接口
@SuperAdminAuth @contextHolder.isSuperAdmin() 要求超管角色（roleName 命中配置） 系统级/跨组织操作
@AssistantAuth hasRole('ASSISTANT') 要求 ASSISTANT 角色 chat 对话微服务
@PublicAccess 无 标记公开访问，无需认证 登录页、公开下载等

注解定义——以 @AdminAuth 为例

// smart-square-common/.../core/annotation/AdminAuth.java
@Target({ElementType.METHOD, ElementType.TYPE})  // 可标注在方法或类上
@Retention(RetentionPolicy.RUNTIME)               // 运行时保留
@PreAuthorize("isAuthenticated()")                // 组合 Spring Security 的 @PreAuthorize
public @interface AdminAuth {}

关键在于 @PreAuthorize("isAuthenticated()") 这一行——它不是注解的属性，而是元注解。当你给方法标了 @AdminAuth，Spring Security 看到的是 @PreAuthorize("isAuthenticated()")，就会在方法调用前检查 SecurityContext 里有没有认证过的身份。

过渡期设计：@AdminAuth、@DeveloperAuth、@AdminOrDeveloperAuth 当前都只要求 isAuthenticated()（登录即可），不区分管理员和开发者。 注释写明「细粒度鉴权待子系统 B 改造」——也就是说，角色区分目前由 JADP 角色门禁在登录时做， 方法级注解只做「是否登录」这道底线检查。未来会加 hasRole('ADMIN') 等细粒度判断。

@SuperAdminAuth——真正有角色判断的注解

// smart-square-common/.../core/annotation/SuperAdminAuth.java
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@PreAuthorize("@contextHolder.isSuperAdmin()")  // 调用 ContextHolder 的方法
public @interface SuperAdminAuth {}

这里 @PreAuthorize 的表达式是 @contextHolder.isSuperAdmin()——@ 前缀表示引用一个 Bean，contextHolder 是 Bean 名，isSuperAdmin() 是方法。Spring Security 会调用这个方法，返回 true 才放行。

这是 SpEL（Spring Expression Language）的用法——@PreAuthorize 不只能用内置函数（isAuthenticated、hasRole），还能调用任意 Bean 的方法。

@PublicAccess——标记公开，不是鉴权

// smart-square-common/.../core/annotation/PublicAccess.java
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
// 注意：没有 @PreAuthorize！
public @interface PublicAccess {}

@PublicAccess 不含 @PreAuthorize，它本身不做任何拦截。它的作用是被 PublicAccessPathScanner 扫描到，然后告诉 SecurityConfig「这个路径放行，不要求认证」。

六、SecurityConfig——路径级授权的守门人

每个下游服务都有自己的 SecurityConfig，配置 Spring Security 的过滤器链。以 admin 为例：

// smart-square-admin/.../config/SecurityConfig.java
@Configuration
@EnableMethodSecurity  // 启用方法级安全（@PreAuthorize 生效的关键）
public class SecurityConfig {

    // 手动维护的白名单
    private static final String[] AUTH_WHITELIST = {
        "/auth/sso/login",        // 登录接口
        "/auth/sso/login-url",
        "/auth/mode",
        "/developers/authorize",  // 开发者 OAuth2 授权
        "/developers/callback",
        "/developers/providers",
        "/developers/oidc/authorize",
        "/developers/oidc/callback",
        "/developers/oidc/providers",
        "/developers/oauth2/token",
        "/ws/acp",                // WebSocket 智能编码
        "/ws/terminal",           // WebSocket 远程终端
        "/cli-providers",         // CLI Provider 列表
        "/skills/*/download",     // Skill 下载
        "/workers/*/download",
        "/workers/*/files/**"
    };

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        // 扫描 @PublicAccess 注解的端点
        List publicEndpoints =
            publicAccessPathScanner.getPublicAccessEndpoints();

        http.cors(Customizer.withDefaults())
            .csrf(AbstractHttpConfigurer::disable)  // 无状态 API，不需要 CSRF
            .sessionManagement(session ->
                session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))  // 无 Session
            .authorizeHttpRequests(auth -> {
                auth.dispatcherTypeMatchers(DispatcherType.ASYNC).permitAll()  // SSE 放行
                    .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()    // CORS 预检放行
                    .requestMatchers(HttpMethod.POST, "/developers").permitAll() // 开发者注册
                    .requestMatchers(AUTH_WHITELIST).permitAll()
                    .requestMatchers(SWAGGER_WHITELIST).permitAll()
                    .requestMatchers(SYSTEM_WHITELIST).permitAll()
                    .requestMatchers(OPEN_API_WHITELIST).permitAll();

                // 动态放行 @PublicAccess 扫描到的端点
                for (PublicAccessEndpoint endpoint : publicEndpoints) {
                    if (endpoint.httpMethod() != null) {
                        auth.requestMatchers(endpoint.httpMethod(), endpoint.path())
                            .permitAll();
                    } else {
                        auth.requestMatchers(endpoint.path()).permitAll();
                    }
                }

                // 其他所有请求要求认证
                auth.anyRequest().authenticated();
            })
            // 未认证时的返回——不是默认的 401 页面，而是 JSON + 登录地址
            .exceptionHandling(ex -> ex.authenticationEntryPoint(
                (request, response, authEx) -> {
                    response.setStatus(401);
                    response.setContentType("application/json;charset=UTF-8");
                    String loginUrl = ssoAuthorizeUrlBuilder.build();
                    response.getWriter().write(
                        "{\"code\":\"UNAUTHORIZED\",\"message\":\"未登录\","
                        + "\"loginUrl\":\"" + loginUrl + "\"}");
                }))
            // 插入身份还原过滤器
            .addFilterBefore(
                new TrustedHeaderAuthenticationFilter(contextHolder),
                UsernamePasswordAuthenticationFilter.class);

        return http.build();
    }
}

关键配置逐行解读

配置 为什么
@EnableMethodSecurity 启用方法级安全，@PreAuthorize 才能生效。没有它，所有 @AdminAuth 都是摆设
STATELESS 无状态——不创建 HttpSession，身份每次请求都从可信头还原
ASYNC.permitAll SSE 流式响应用 ASYNC 派发，不能被 Spring Security 拦截
OPTIONS.permitAll CORS 预检请求不带 token，必须放行
anyRequest().authenticated() 默认拒绝策略——不在白名单的路径都要求认证（fail-closed）
addFilterBefore(TrustedHeaderAuthenticationFilter) 在 Spring Security 标准的 UsernamePasswordAuthenticationFilter 之前插入身份还原
401 返回 loginUrl 前端拿到 401 时能直接跳 SSO 登录页，不用硬编码地址

chat 模块的 SecurityConfig——区分 401 和 403

// smart-square-chat/.../config/ChatSecurityConfig.java
private static final String UNAUTHORIZED_BODY =
    "{\"code\":\"UNAUTHORIZED\",\"message\":\"登录已失效，请重新登录\",\"data\":null}";
private static final String FORBIDDEN_BODY =
    "{\"code\":\"FORBIDDEN\",\"message\":\"无权访问该资源\",\"data\":null}";

// 401：未认证（token 无效或缺失）
static final AuthenticationEntryPoint UNAUTHORIZED_ENTRY_POINT =
    (request, response, authEx) -> writeError(response, HttpStatus.UNAUTHORIZED, UNAUTHORIZED_BODY);

// 403：已认证但无权限（如 ASSISTANT 角色调用管理员接口）
static final AccessDeniedHandler ACCESS_DENIED_HANDLER =
    (request, response, deniedEx) -> writeError(response, HttpStatus.FORBIDDEN, FORBIDDEN_BODY);

chat 模块明确区分了 401（未认证）和 403（已认证但无权限）。admin 模块只配了 401 入口，因为 admin 的 @AdminAuth 过渡期只检查 isAuthenticated()，不会产生 403。

七、PublicAccessPathScanner——自动发现公开端点

白名单维护是个麻烦事——每加一个公开接口就得改 SecurityConfig。PublicAccessPathScanner 解决了这个问题：启动时扫描所有 @RestController，找到标注了 @PublicAccess 的方法，自动注册到白名单。

// smart-square-common/.../security/PublicAccessPathScanner.java
@Override
public void setApplicationContext(ApplicationContext applicationContext) {
    Set endpoints = new HashSet<>();
    String[] beanNames = applicationContext.getBeanNamesForAnnotation(RestController.class);
    for (String beanName : beanNames) {
        scanController(applicationContext.getType(beanName), endpoints);
    }
    publicAccessEndpoints = endpoints;
}

private void scanController(Class controllerClass, Set endpoints) {
    String[] classLevelPaths = getClassLevelPaths(controllerClass);
    boolean classLevelPublic = AnnotatedElementUtils.hasAnnotation(controllerClass, PublicAccess.class);

    for (Method method : controllerClass.getDeclaredMethods()) {
        boolean hasAuthAnnotation = hasAuthAnnotation(method, controllerClass);
        boolean methodLevelPublic = AnnotatedElementUtils.hasAnnotation(method, PublicAccess.class);

        // 鉴权注解优先级高于 @PublicAccess
        if (hasAuthAnnotation) continue;

        if (methodLevelPublic || classLevelPublic) {
            HttpMethod[] httpMethods = getHttpMethods(method);
            String[] methodPaths = getMethodLevelPaths(method);
            // 拼接类级路径 + 方法级路径，添加到白名单
        }
    }
}
优先级规则：如果方法同时标了 @AdminAuth 和 @PublicAccess， @AdminAuth 赢——该方法不加入白名单，仍需认证。 这是 fail-closed 设计：宁可误拦，不可误放。

八、两层授权——路径级 vs 方法级

现在可以完整理解授权的两个层次了：

第一层：路径级（SecurityConfig 配置）

请求到达时，Spring Security 先检查路径：

  • 在白名单里（AUTH_WHITELIST / @PublicAccess 扫描）→ permitAll() 放行
  • 不在白名单 → anyRequest().authenticated() → 检查 SecurityContext 有没有身份
  • 有身份 → 进入下一层
  • 无身份 → 401（未认证）

第二层：方法级（@PreAuthorize 注解）

路径检查通过后，进入 Controller 方法前，@PreAuthorize 再做一次检查：

  • isAuthenticated() → 检查是否已认证（@AdminAuth、@DeveloperAuth）
  • hasRole('ASSISTANT') → 检查 authorities 是否包含 ROLE_ASSISTANT（@AssistantAuth）
  • @contextHolder.isSuperAdmin() → 调用 Bean 方法检查 roleName（@SuperAdminAuth）
  • 检查通过 → 执行方法
  • 检查不通过 → 403（已认证但无权限）
两层防御的意义：路径级是粗粒度的（谁能访问这组接口）， 方法级是细粒度的（这个具体操作需要什么角色）。 即使路径级白名单配错了，方法级注解还能兜底——反之亦然。

九、PermissionProperties——超管角色配置

// smart-square-common/.../config/properties/PermissionProperties.java
@Data
@Component
@ConfigurationProperties(prefix = "permission")
public class PermissionProperties {
    /**
     * 超管角色名（OR：用户 JADP 角色名与该集合有交集即超管）
     * 匹配 roleName 而非 roleId
     * 默认空集 = 无人是超管（fail-closed），须由各环境配置显式赋值
     */
    private List superAdminRoles = new ArrayList<>();
}

配置在 application.yml 里：

permission:
  super-admin-roles:
    - 应用广场超级管理员
    - 知识平台超级管理员

默认空集 = 无人是超管。这是 fail-closed 设计——忘了配置不会导致所有人都变成超管，而是所有人都不是超管。

十、总结——完整授权链路

认证（网关） 授权（下游） ────────── ──────── 浏览器 ──► AuthGlobalFilter ──► TrustedHeaderAuthFilter ──► SecurityConfig ──► @PreAuthorize ──► Controller │ │ │ │ │ 剥离伪造头 │ 读 X-User-* 头 │ 路径级检查 │ 方法级检查 │ 验 JWT/查 Redis │ 构建 Authentication │ 白名单放行 │ isAuthenticated() │ 注入 X-User-* 头 │ 存 SecurityContext │ 其他要求认证 │ hasRole() │ │ 存 ContextHolder │ 无身份 → 401 │ isSuperAdmin() │ │ │ │ 无权限 → 403 │ │ │ │ │ 认证失败 → 401 │ │ │ │ 不做授权判断 │ │ │
一句话总结：网关认证后注入 X-User-* 头 → TrustedHeaderAuthenticationFilter 还原为 Spring Security 身份 → SecurityConfig 做路径级白名单检查 → @PreAuthorize（通过 @AdminAuth 等元注解）做方法级角色检查 → 全部通过才执行 Controller 方法。

  4. 没有特别原因，只是历史遗留
查看答案

B。@PreAuthorize 从 SecurityContextHolder 读身份；业务代码（Service 层）通过 ContextHolder 拿 orgCode、roleNames 更方便。两者存的是同一份身份。

3. @SuperAdminAuth 的 @contextHolder.isSuperAdmin() 判定依据是什么？
  1. 用户的 roleCode 是否匹配配置
  2. 用户的 roleName 是否与 permission.super-admin-roles 有交集
  3. 用户的 userType 是否为 ADMIN
  4. 用户是否通过了 JADP 登录
查看答案

B。isSuperAdmin() 检查 getRoleNames() 与 permission.super-admin-roles 配置列表是否有交集。用 roleName 而非 roleCode，因为 JADP 的 roleCode 是不可读随机串。

4. 如果一个方法同时标了 @AdminAuth 和 @PublicAccess，会发生什么？
  1. 公开访问，无需登录
  2. 需要登录（@AdminAuth 优先级更高）
  3. 报错，不能同时标两个注解
  4. 取决于配置文件里的优先级设置
查看答案

B。PublicAccessPathScanner 扫描时，如果检测到鉴权注解（@AdminAuth 等），会跳过该方法，不加入白名单。所以 @AdminAuth 赢，方法仍需认证。这是 fail-closed 设计。

5. SSE 流式响应时，ContextHolder 的 ThreadLocal 丢了怎么办？
  1. SSE 不需要身份信息，无所谓
  2. 回退到 SecurityContext 的 Authentication.details（HostSsoUser）获取
  3. 重新从网关获取身份头
  4. 用 Redis 缓存的身份快照
查看答案

B。ContextHolder 的 getOrgCode() 等方法优先从 ThreadLocal 取，取不到时回退到 SecurityContextHolder.getContext().getAuthentication().getDetails()，从中取出 HostSsoUser 获取身份信息。

十二、关键设计决策回顾

决策 为什么
网关认证，下游授权 网关只管「你是谁」，下游管「你能干什么」——职责分离
身份头防伪造 网关先剥离外部同名头再注入，下游必须经过网关才能获得身份
角色判定用 roleName JADP 的 roleCode 是不可读随机串，只有 roleName 可读可配置
过渡期只检查 isAuthenticated() 角色区分由 JADP 门禁在登录时做，方法级注解只做底线检查，待后续细化
SSE 异步回退到 Authentication.details ThreadLocal 在线程切换时丢失，SecurityContext 跨线程仍可访问
@PublicAccess 自动扫描 不用手动维护白名单，加注解即可
鉴权注解优先于 @PublicAccess fail-closed——宁可误拦不可误放
superAdminRoles 默认空集 fail-closed——忘了配置不会让所有人变超管
401 返回 loginUrl 前端可直接跳登录页，不用硬编码
