第 4 课 · Nacos 注册发现与配置中心

课程 · ← 上一节：Maven 多模块 · 全景图 · 学习使命

目标：理解 Nacos 在这个项目里的两个角色——服务注册发现和配置管理。 学完后你能回答：gateway 怎么找到 admin/chat？chat 怎么调 admin？ 多个开发者的本地服务怎么互不干扰？

一、Nacos 是什么，为什么用它

在单体架构里，所有代码在一个进程内，方法调用就是函数调用。拆成微服务后， admin 在 8090、chat 在 8091、gateway 在 8081——它们怎么找到彼此？

最笨的办法：写死 IP 和端口。但服务重启可能换端口，扩容会加实例，写死根本维护不过来。

Nacos 的办法：所有服务启动时把自己注册到 Nacos（「我叫 smart-square-admin，我在 192.168.1.10:8090」）， 要调别的服务时问 Nacos（「smart-square-admin 在哪？」），Nacos 返回可用实例列表，调用方自己选一个。

Nacos 在这个项目里同时承担两个角色：
  1. 服务注册发现：服务上下线时自动通知，调用方动态获取实例地址
  2. 配置中心：集中管理配置，配置变更可动态推送（本项目主要用注册发现，配置仍以 yml 为主）
用一个组件解决两个问题，减少基础设施数量——这是选 Nacos 而非 Eureka + Spring Cloud Config 的原因。

二、服务注册：每个服务启动时做了什么

上一课你看到了 admin 启动类上的 @EnableDiscoveryClient。这个注解开启服务注册。 具体注册到哪？看 application-dev.yml：

# admin 的 application-dev.yml
spring:
  application:
    name: smart-square-admin          # ← 服务名，注册到 Nacos 的名字
  cloud:
    nacos:
      discovery:
        server-addr: ${NACOS_ADDR:8.166.117.70:8848}   # ← Nacos 地址
        namespace: ${NACOS_NAMESPACE:}                  # ← 命名空间（隔离用）
        group: ${NACOS_GROUP:DEFAULT_GROUP}             # ← 分组
        username: ${NACOS_USERNAME:nacos}
        password: ${NACOS_PASSWORD:Zenflux@123}
三个关键配置：
  • spring.application.name——服务名，是注册到 Nacos 的唯一标识。 gateway 路由里写的 lb://smart-square-chat 用的就是这个名字
  • server-addr——Nacos 服务器地址，本项目用远程的 8.166.117.70:8848
  • namespace——命名空间，隔离不同环境的服务实例

chat 和 gateway 的配置几乎一样，只是 application.name 不同：

# chat    → name: smart-square-chat     port: 8091
# gateway → name: smart-square-gateway   port: 8081
# sso     → name: smart-square-sso       port: 8095
# admin   → name: smart-square-admin     port: 8090
# knowledge→ name: smart-square-knowledge port: 8093

三、命名空间隔离——多开发者互不干扰

这是你在本地开发时会直接遇到的问题。看 local/AGENTS.md 的记录：

真实场景：远程 Docker 容器注册到 Nacos public 命名空间， 你的本地服务如果也注册到 public，gateway 路由时可能把请求转发到你的本地 admin—— 别人的请求就被你的本地服务处理了，互相干扰。

解决方案：本地服务注册到 dev_ykh 命名空间（ID: cfa45b82-...）， 通过各模块的 application-local.yml 配置。两个命名空间的服务实例互相不可见，互不影响。 
# application-local.yml（本地开发覆盖，不入 Git）
spring:
  cloud:
    nacos:
      discovery:
        namespace: cfa45b82-c7b7-4330-8778-4568c7b85dca   # dev_ykh
      config:
        namespace: cfa45b82-c7b7-4330-8778-4568c7b85dca
命名空间是 Nacos 的一级隔离机制。不同命名空间的服务实例完全隔离—— 注册不可见、发现不可见。这让你可以在本地跑一套完整的服务栈，不影响线上，也不被线上影响。

group 是命名空间内的二级分组，本项目都用 DEFAULT_GROUP，没做进一步细分。

四、服务发现：gateway 怎么找到 admin/chat

看 gateway 的路由配置——这是 Nacos 服务发现最直接的应用：

# gateway 的 application-dev.yml
spring:
  cloud:
    gateway:
      server:
        webflux:
          discovery:
            locator:
              enabled: false    # 关闭基于服务名的自动路由，只用下方显式路由
          routes:
            # /chat/** → smart-square-chat（SSE 长连接，禁用响应超时）
            - id: smart-square-chat
              uri: lb://smart-square-chat
              predicates:
                - Path=/chat/**
              metadata:
                response-timeout: -1

            # /sso/** → smart-square-sso
            - id: smart-square-sso
              uri: lb://smart-square-sso
              predicates:
                - Path=/sso/**

            # 其余全部流量 → smart-square-admin（catch-all，必须放最后）
            - id: smart-square-admin
              uri: lb://smart-square-admin
              predicates:
                - Path=/**
lb://smart-square-chat 是什么意思：
  • lb = Load Balancer，告诉 gateway「这不是固定地址，要去 Nacos 查」
  • smart-square-chat = 要查的服务名（就是 chat 注册时的 spring.application.name）
  • gateway 启动时从 Nacos 拉取服务实例列表，请求来时按负载均衡策略选一个实例转发
如果 chat 部署了 3 个实例，gateway 会自动在 3 个之间轮询——这就是微服务扩容的基础。
路由顺序很重要：Path=/** 的 catch-all 路由必须放最后。 Spring Cloud Gateway 按声明顺序匹配，如果 catch-all 在前面，所有请求都会被它吃掉， /chat/** 和 /sso/** 永远匹配不到。
SSE 路由的特殊处理：/chat/** 和 /knowledge/qa/** 路由设了 response-timeout: -1（禁用超时）。因为 AI 对话是 SSE 流式长连接—— 模型生成一个字就推一个字，可能持续几十秒。如果用默认的 30 秒超时，对话还没完就被 gateway 切断了。

五、服务间调用：chat 怎么调 admin

gateway → admin/chat 是「外部请求经网关路由」。但 chat 还要调 admin 拿产品数据—— 这是服务间调用，用 OpenFeign。看真实代码：

1. Feign 客户端接口（chat 侧）

// chat 模块：ProductClient.java
@FeignClient(name = "${internal.server-service:smart-square-admin}", contextId = "productClient")
public interface ProductClient {

    @GetMapping("/internal/products/{productId}")
    Response<ProductBriefResult> getProduct(@PathVariable("productId") String productId);

    @GetMapping("/internal/products/batch")
    Response<List<ProductBriefResult>> getProducts(@RequestParam("ids") List<String> ids);
}
Feign 的「魔法」：你只写接口，不写实现。Feign 在运行时自动生成实现类：
  • @FeignClient(name = "smart-square-admin")——告诉 Feign 调用名为 smart-square-admin 的服务
  • @GetMapping("/internal/products/{productId}")——调用时发 HTTP GET 请求到这个路径
  • 服务名 smart-square-admin 通过 Nacos 解析成实际 IP:端口
  • 返回值 Response<ProductBriefResult> 自动反序列化
对你来说就像调本地方法，实际是跨进程 HTTP 调用。这就是「声明式 HTTP 客户端」。

2. 被调方接口（admin 侧）

// admin 模块：ChatInternalController.java
@RestController
@RequestMapping("/internal")
public class ChatInternalController {

    @GetMapping("/products/{productId}")
    @PublicAccess
    public ProductBriefResult getProduct(@PathVariable String productId) {
        // 查数据库返回产品概要
    }
}
为什么 internal 接口标 @PublicAccess： /internal/** 端点仅集群内可达、不经网关对外暴露。 它不走外部鉴权（因为只有 chat 通过 Feign 调它，不是终端用户直接调）。 @PublicAccess 让它跳过对外鉴权，但身份信息通过可信头透传（下面讲）。

3. 身份头透传——Feign 拦截器

chat 调 admin 时，admin 怎么知道是哪个用户在操作？答案：透传网关注入的可信身份头。

// chat 模块：FeignIdentityHeaderInterceptor.java
@Component
public class FeignIdentityHeaderInterceptor implements RequestInterceptor {

    private static final String[] PROPAGATED_HEADERS = {
        TrustedHeaders.USER_ID,      // X-User-Id
        TrustedHeaders.USER_TYPE,    // X-User-Type
        TrustedHeaders.ORG_CODE,     // X-Org-Code
        TrustedHeaders.USER_NAME,    // X-User-Name
        TrustedHeaders.TRACE_ID      // X-Trace-Id
    };

    @Override
    public void apply(RequestTemplate template) {
        HttpServletRequest request = currentRequest();  // 拿到 chat 当前收到的请求
        if (request == null) return;
        for (String header : PROPAGATED_HEADERS) {
            String value = request.getHeader(header);
            if (StrUtil.isNotBlank(value)) {
                template.header(header, value);  // 透传给 admin
            }
        }
    }
}
完整的身份传递链：
  1. 用户请求到 gateway，gateway 校验 JWT/JADP，注入 X-User-Id 等可信头
  2. gateway 转发给 chat，chat 收到带可信头的请求
  3. chat 通过 Feign 调 admin，FeignIdentityHeaderInterceptor 把可信头原样透传
  4. admin 收到 /internal/** 请求，从可信头还原用户身份，做权限过滤
关键前提：下游服务信任这些头，是因为网关在转发前剥离了外部伪造的同名头， 且下游不可绕过网关直达（由部署层网络策略保证）。这就是 TrustedHeaders 类注释里写的约定。

六、可信头——TrustedHeaders 常量

所有可信头定义在 common 模块的 TrustedHeaders.java，供 gateway/admin/chat 共享：

头名含义谁注入
X-User-Id用户唯一标识gateway
X-User-Name用户姓名gateway
X-Org-Code所属组织编码gateway
X-User-Type用户类型（ADMIN/DEVELOPER/ASSISTANT）gateway
X-User-Roles角色编码列表（逗号分隔）gateway
X-User-Role-Names角色名称列表（角色判定的唯一判据）gateway
X-Trace-Id全链路追踪 IDgateway
X-Open-Client-Id开放 API 客户端标识gateway
为什么角色判定用 roleName 而非 roleId：JADP 的 roleId 是不可读随机串 （如 47DB3AED9CE544009D3209CF67717402），不适合写进配置。 所以角色相关配置一律以角色名表达（如「应用广场超级管理员」）， X-User-Role-Names 头承载角色名列表，是平台各处角色判定的唯一判据。
