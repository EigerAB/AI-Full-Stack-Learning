一、它是什么

SmartSquare 是一个 AI 开放平台，把 LLM、MCP Server、Agent、Skill、Tool 等 AI 能力 统一管理、分发、计量。它同时提供 AI 编程助手（云端沙箱编程）和智能对话助手（AG-UI 协议流式对话）。

后端是一个 Maven 多模块微服务架构，从早期的 dal/server/bootstrap 三层单体 演进而来，现在拆成网关 + 主服务 + 对话微服务 + 公共库 + gRPC 契约五个核心模块， 经 Nacos3 注册与发现。

三、技术栈分层

1. 网关层 — 统一入口

负责：集中鉴权、身份注入、路由转发。不写业务逻辑。

Spring Cloud Gateway WebFlux (响应式) Reactor Nacos 3.2.1 服务发现

  • 为什么用 WebFlux 而不是 WebMVC：网关要做大量非阻塞转发，响应式模型天然适合；且 Spring Cloud Gateway 本身就是基于 WebFlux 构建。
  • 为什么鉴权集中在网关：下游服务可以信任网关注入的 X-User-* 头，不必每个服务重复实现 JADP/JWT 校验逻辑。

2. 业务层 — 主服务与对话微服务

负责：所有业务逻辑、REST API、AI 对话编排、智能编码。

Spring Boot 3.5.9 Spring Web MVC Spring Security Spring Cloud OpenFeign Spring AI 1.1.8 OpenAI Java SDK 4.6.1 DashScope 2.22.4 Google GenAI 1.34.0 gRPC 1.60.1 Protobuf 3.25.2

  • 为什么 admin 用 WebMVC 而 gateway 用 WebFlux：admin 承载传统 CRUD 业务，阻塞式模型更简单直观；gateway 才需要响应式做高并发转发。两种模型在同一个系统里按职责分工。
  • 为什么 chat 拆成独立微服务：AI 对话是长连接、流式、重 IO 的场景，与 admin 的 CRUD 负载特征完全不同，独立部署便于独立扩缩容和故障隔离。
  • 为什么 chat 用 OpenFeign 调 admin 而不直连数据库：保持数据归属唯一——Product/权限数据归 admin 管，chat 只能通过接口拿，避免数据库耦合。
  • 为什么用 gRPC 做意图识别：意图识别是高频、低延迟的跨服务调用，gRPC 的二进制协议比 HTTP/JSON 更省带宽、更快。
  • 为什么集成 3 个 AI SDK：OpenAI / DashScope(通义) / Google Gemini 对接不同模型供应商，平台要支持多模型分发。

3. 公共基础设施层 — 共享契约

负责：admin 与 chat 共享的工具、响应格式、事件定义、gRPC 契约。

Hutool 5.8.33 Caffeine 3.2.3 (本地缓存) OkHttp 4.12.0 Guava Retrying 2.0.0 BouncyCastle 1.78 (加密) Apache Tika 2.9.2 (文档解析) MinIO 8.5.17 (对象存储)

  • 为什么单独抽 common 模块：避免 admin 和 chat 各自重复造轮子，统一响应格式 Response<T> 和异常体系，让前端对接一致。
  • 为什么 gRPC 契约单独成模块：.proto 文件编译出的 stub 要被 admin 和 chat 同时依赖，单独模块让两边引用同一份契约，避免定义漂移。
  • 为什么用 Caffeine 而不是 Redis 做本地缓存：高频读取且不需要跨实例一致的数据（如配置元数据）用本地缓存更快；跨实例共享的才用 Redis。

4. 数据层 — 持久化与迁移

负责：ORM、数据库、结构演进。

MyBatis-Plus 3.5.9 DM8 达梦数据库 Flyway 10.15.0 db-migration-dameng-flyway Redis (会话/缓存)

  • 为什么用 MyBatis-Plus 而不是 JPA/Hibernate：MyBatis-Plus 对 SQL 的控制更精细，适配国产数据库达梦的方言更灵活；JPA 的自动建表在国产库上兼容性差。
  • 为什么用达梦而不是 MySQL：信创/国产化要求——金融、政企场景通常强制要求国产数据库。
  • 为什么用 Flyway 而不是自动建表：数据库结构变更必须可追溯、可回滚、可审计，Flyway 的版本化迁移脚本让 schema 演进有据可查。
  • 为什么需要 db-migration-dameng-flyway 适配包：Flyway 官方不直接支持达梦，这个第三方包补上了达梦方言支持。

5. 运维与质量层

负责：部署、文档、代码质量、测试。

Maven 多模块 Spotless + Google Java Format (AOSP) JUnit + jqwik 1.9.2 (属性测试) springdoc-openapi 2.8.17 Docker Compose / Helm / Podman Nacos 3.2.1 (注册+配置) Fabric8 K8s Client Aliyun SLS (日志可观测)

  • 为什么用 Spotless 而不是 Checkstyle：Spotless 能直接用 Google Java Format 自动格式化代码，不只是检查；CI 上 make lint-fix 一键修复，降低格式争议。
  • 为什么用 jqwik 做属性测试：传统单元测试只能覆盖想到的 case，属性测试让框架自动生成大量随机输入，更容易暴露边界 bug。
  • 为什么三种部署方式：Docker Compose 给开发本地、Helm 给生产 K8s、Podman 给无 Docker 环境，按场景选择。

四、关键架构设计决策一览

设计决策选择核心原因
服务拆分网关 + 主服务 + 对话微服务按负载特征隔离：CRUD vs 长连接流式
服务发现Nacos 3.2.1同时做注册中心和配置中心，减少组件数
网关模型WebFlux 响应式高并发非阻塞转发
业务模型WebMVC 阻塞式CRUD 场景简单直观
跨服务调用OpenFeign (HTTP) + gRPC业务数据走 Feign，低延迟意图识别走 gRPC
鉴权位置网关集中 + 下游注解网关注入可信头，下游用 @AdminAuth 等注解做角色控制
数据库达梦 DM8信创国产化要求
ORMMyBatis-PlusSQL 可控，国产库方言适配灵活
Schema 演进Flyway 版本化迁移结构变更可追溯可审计
模块间通信Spring Events 领域事件松耦合，删除等操作触发跨域清理
统一响应ResponseAdvice 自动包装Controller 直接返回业务对象，框架统一包 Response<T>
异常处理ExceptionAdvice + BusinessException禁止用 null 表示业务错误，统一抛异常

六、学习路径建议

  1. 本图——先记住五层结构和「为什么」
  2. Spring Boot 基础锚定到 admin 的 application.yml 和一个 Controller 链路

  4. 认证授权：JWT → AuthGlobalFilter → 角色注解 → SSO/OAuth2
  5. （后续）AI 协议、智能编码、数据持久化、可观测
