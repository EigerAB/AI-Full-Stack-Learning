你纠正得对。刚才的问题应该被理解为“架构发现问题”，不是让你马上做技术选型或定案。

当前阶段更适合建立：

1. 业务中台能力地图；
2. 架构设计时需要回答的问题清单；
3. 领域模型和专业术语表；
4. 最后再基于这些知识形成具体系统设计。

你刚才确认的内容，暂时只作为我们的“案例假设”，不是最终架构决策。

## 一、先建立整体能力地图

一个平台型 SaaS 业务中台，通常可以拆成以下几类能力。

```
平台基础层
├── 租户与组织
├── 用户与身份
├── 角色与权限
├── 项目与工作空间
├── 应用与环境
└── 配额、套餐与功能开关

平台支撑层
├── API 与集成
├── 工作流与审批
├── 消息与通知
├── 文件与内容
├── 搜索
├── 配置与字典
└── 任务调度

治理与安全层
├── 审计日志
├── 操作记录
├── 数据隔离
├── 安全策略
├── 监控与告警
├── 备份与灾备
└── 合规治理

业务域层
├── 客户业务
├── 订单业务
├── 项目业务
├── 财务业务
└── 其他可复用业务能力
```

其中最重要的原则是：

> 中台不应该承接所有业务，而应该承接跨多个项目复用、规则相对稳定、需要统一治理的能力。

否则很容易演化成一个所有业务都依赖的“大泥球系统”。

## 二、设计前需要考虑哪些问题

### 1. 业务边界问题

首先要判断：

- 哪些能力是所有项目都需要的？
- 哪些能力只是某一个业务项目的专属逻辑？
- 哪些数据由哪个系统作为唯一事实来源？
- 中台是提供能力，还是直接拥有业务数据？
- 业务项目之间是否允许直接访问彼此的数据？
- 中台是否需要承接跨项目流程？

这里会涉及几个术语：

- **Domain：领域**，例如订单、客户、项目、权限。
- **Bounded Context：限界上下文**，一个业务概念在某个边界内有明确含义。
- **Domain Service：领域服务**，负责某个业务领域的规则。
- **Shared Capability：共享能力**，多个业务都可以复用的能力。
- **Source of Truth：事实来源**，某类数据最终以哪个系统为准。
- **Core Domain：核心域**，最能体现产品竞争力的业务。
- **Generic Subdomain：通用子域**，例如组织、权限、通知。

例如，“用户”在身份系统中代表登录身份，在项目系统中代表项目成员，在审批系统中又可能代表审批人。它们不能简单地都叫同一个 `User`。

### 2. 多租户问题

需要思考：

- 什么是租户？
- 租户和客户企业是否完全等价？
- 一个租户是否可以拥有多个组织、部门、工作空间和项目？
- 是否存在集团租户和子租户？
- 一个用户能否加入多个租户？
- 用户切换租户时，权限和数据上下文如何变化？
- 是否允许跨租户协作？
- 平台运营人员是否可以跨租户操作？
- 租户被暂停、删除、归档时，数据怎么处理？
- 租户之间是否有不同套餐、配额和功能？

常见术语：

|术语|含义|
|---|---|
|Tenant|租户，数据和权限隔离的基本边界|
|Customer / Account|客户或商业账户，不一定等于技术上的 Tenant|
|Organization|组织，通常描述企业内部人员归属|
|Workspace|工作空间，通常描述协作边界|
|Project|项目，通常描述一项业务或工作集合|
|Tenant Context|当前请求所处的租户上下文|
|Tenant Isolation|租户隔离|
|Noisy Neighbor|某个租户占用过多资源，影响其他租户|
|Tenant-aware|组件或服务具备租户意识|
|Tenant Silo|每个租户拥有独立资源|
|Tenant Pool|多个租户共享资源，通过逻辑方式隔离|

这里要特别区分：

```
用户归属组织
项目决定协作范围
租户决定数据和管理边界
```

### 3. 身份与 SSO 问题

需要考虑：

- 平台是否保存密码？
- 企业使用什么身份源？
- 支持 OIDC、SAML 还是 LDAP？
- 企业用户第一次登录时是否自动创建？
- 用户从企业离职后，平台如何立即禁用？
- 企业组织结构是否同步到平台？
- 一个用户加入多个租户时，如何选择当前租户？
- 是否支持 MFA 和二次认证？
- 平台运营账号和企业业务账号是否分离？
- 服务之间是否需要机器身份认证？

专业术语：

|术语|含义|
|---|---|
|Authentication / AuthN|身份认证，确认“你是谁”|
|Authorization / AuthZ|权限授权，确认“你能做什么”|
|Identity|身份记录|
|User|人类用户|
|Principal / Subject|权限系统中的主体，可以是用户、服务账号或设备|
|Membership|用户与租户、组织或项目之间的成员关系|
|IdP|Identity Provider，身份提供商|
|SP / RP|服务提供方 / OIDC 依赖方|
|Federation|身份联邦，信任外部身份系统|
|SSO|Single Sign-On，单点登录|
|JIT Provisioning|用户首次登录时即时创建账号|
|Provisioning|创建或同步用户|
|Deprovisioning|移除或禁用用户|
|SCIM|用于自动同步用户和组织成员生命周期的协议|
|Service Account|服务账号，供程序调用而非人登录|
|Workload Identity|工作负载身份，例如服务、容器或任务身份|

协议的关系可以这样记：

```
OAuth 2.0：授权框架
OIDC：基于 OAuth 2.0 的身份认证协议
SAML 2.0：企业常用的身份联邦协议
LDAP / AD：企业目录与账号系统
SCIM：用户和组织成员同步协议
```

### 4. 权限与鉴权问题

需要考虑：

- 权限控制到菜单、按钮、接口，还是数据？
- 权限作用域是平台、租户、组织、工作空间还是项目？
- 角色是否可以继承？
- 用户是否可以同时拥有多个角色？
- 项目负责人能否临时授权给其他人？
- 是否存在“只能查看自己部门数据”这种数据权限？
- 是否需要字段级权限？
- 是否需要按金额、状态、地域等条件授权？
- 租户管理员能否管理平台管理员？
- 是否需要权限审批和权限有效期？
- 权限变更是否需要实时生效？
- 默认拒绝还是默认允许？

核心术语：

|术语|含义|
|---|---|
|RBAC|基于角色的访问控制|
|ABAC|基于属性的访问控制|
|ReBAC|基于用户与资源关系的访问控制|
|PBAC|基于策略的访问控制|
|Permission|权限，例如 `project:read`|
|Resource|资源，例如项目、订单、文件|
|Action|动作，例如读取、编辑、删除、审批|
|Scope|权限作用域|
|Policy|授权策略|
|Claim|Token 中描述身份或权限的声明|
|PDP|Policy Decision Point，策略决策点|
|PEP|Policy Enforcement Point，策略执行点|
|PAP|Policy Administration Point，策略管理点|
|Least Privilege|最小权限原则|
|Separation of Duties|职责分离|
|Delegated Administration|委托管理员|
|Permission Inheritance|权限继承|
|Deny Override|拒绝优先|

可以先形成这个抽象：

```
Subject + Resource + Action + Context → Allow / Deny
```

例如：

```
用户张三
+ 项目 P100
+ edit
+ 当前租户、所属部门、项目成员关系
→ 是否允许
```

### 5. 数据隔离问题

需要考虑的不只是业务数据库：

- 数据库如何隔离？
- 缓存 Key 是否包含租户信息？
- 搜索索引如何隔离？
- 文件和对象存储路径如何隔离？
- 消息队列中的事件是否携带租户信息？
- 日志是否可能泄露其他租户数据？
- 导出任务是否可能跨租户？
- 管理后台是否有跨租户查询能力？
- 备份恢复能否恢复单个租户？
- 租户数据是否需要单独加密密钥？
- 是否存在数据驻留区域要求？

常见隔离模型：

```
共享数据库 + 共享表 + tenant_id
共享数据库 + 独立 Schema
独立数据库
独立部署
```

相关术语：

- **Row-Level Security / RLS**：行级安全。
- **Data Residency**：数据驻留区域。
- **Data Partitioning**：数据分区。
- **Encryption at Rest**：静态数据加密。
- **Encryption in Transit**：传输过程加密。
- **KMS**：密钥管理服务。
- **Blast Radius**：故障或安全事件影响范围。

### 6. 平台治理问题

业务中台通常还需要承接：

- 租户创建、启用、暂停、注销；
- 套餐和能力开通；
- 功能开关；
- 用户数、存储量、调用量配额；
- API 限流；
- 服务版本管理；
- 应用注册；
- 环境管理；
- 配置管理；
- 字典和枚举管理；
- 变更审批；
- 操作审计。

这里会遇到：

- **Entitlement**：某个租户被授予的能力。
- **Quota**：额度限制，例如用户数、存储量。
- **Rate Limit**：访问频率限制。
- **Feature Flag**：功能开关。
- **Plan**：套餐或产品计划。
- **Control Plane**：管理和配置平面。
- **Data Plane**：实际承载业务请求和数据处理的平面。

一个重要的架构分层是：

```
Control Plane：
管理租户、用户、权限、配置、策略、版本

Data Plane：
处理真实业务数据和业务请求
```

### 7. 集成与开放能力

中台往往不是孤立系统，需要考虑：

- 是否提供开放 API？
- 外部系统如何认证？
- API 如何版本化？
- 是否支持 Webhook？
- 是否需要事件总线？
- 同步调用失败如何重试？
- 消息是否可能重复？
- 操作是否需要幂等？
- 跨服务事务如何处理？
- 外部系统故障时，业务如何降级？

专业术语：

- **API Gateway**：统一入口、路由、认证、限流。
- **BFF**：Backend for Frontend，面向特定前端的后端。
- **Webhook**：事件发生后回调外部系统。
- **Event Bus**：事件总线。
- **Message Broker**：消息代理。
- **Idempotency**：幂等性。
- **Outbox Pattern**：保证业务写入和事件发布一致。
- **Saga**：分布式事务编排模式。
- **Circuit Breaker**：熔断。
- **Retry with Backoff**：带退避的重试。
- **Contract Testing**：契约测试。

### 8. 工作流、通知和文件

很多业务项目都会重复需要这些能力：

- 审批流；
- 状态流转；
- 任务分派；
- 定时任务；
- 邮件、短信、站内信、企业微信或钉钉通知；
- 文件上传、预览、下载和权限控制；
- 模板管理；
- 导入导出；
- 批量处理。

需要区分：

- **Workflow**：流程定义和状态流转。
- **BPM**：业务流程管理。
- **State Machine**：状态机。
- **Human Task**：需要人工处理的任务。
- **Notification Template**：通知模板。
- **Object Storage**：对象存储。
- **Content Metadata**：文件或内容的元数据。

### 9. 可观测性与可靠性

还要考虑：

- 如何知道某个租户的请求变慢了？
- 如何定位一次跨服务请求？
- 如何统计接口成功率？
- 如何设置告警？
- 租户之间是否有资源隔离？
- 服务不可用时能否降级？
- 数据库故障后如何恢复？
- 备份多久保留？
- 能接受丢失多少数据？
- 能接受中断多久？

术语：

|术语|含义|
|---|---|
|Logging|日志|
|Metrics|指标|
|Tracing|链路追踪|
|Observability|可观测性|
|SLI|服务级指标|
|SLO|服务目标|
|SLA|对外服务承诺|
|HA|高可用|
|DR|灾备|
|RPO|可接受的数据丢失时间范围|
|RTO|可接受的恢复时间|
|Graceful Degradation|优雅降级|
|Backpressure|背压|
|Cell Architecture|按单元隔离故障影响的架构|


## 三、推荐的学习顺序

建议按下面顺序学习，而不是一开始就研究微服务、数据库分库或微前端：

1. **领域建模**：Tenant、Organization、Workspace、Project、User、Membership。
2. **多租户 SaaS 基础**：租户上下文、生命周期、数据隔离。
3. **身份认证**：IdP、SSO、OAuth 2.0、OIDC、SAML、LDAP、SCIM。
4. **权限授权**：RBAC、ABAC、ReBAC、PDP、PEP、策略继承。
5. **平台治理**：套餐、配额、功能开关、限流、审计。
6. **开放集成**：API Gateway、Webhook、事件、幂等、最终一致性。
7. **可靠性与安全**：可观测性、RPO/RTO、灾备、密钥、审计。
8. **系统架构选型**：模块化单体、微服务、微前端、控制面/数据面。
9. **最后才形成具体设计**：组件、数据模型、接口、流程和部署架构。

目前我们已经有了一组不错的案例假设：

```
平台型 SaaS
一个全局用户可以加入多个租户
租户下有组织、工作空间和项目
企业 IdP 负责认证
LDAP/AD/SCIM 负责用户生命周期
权限采用 RBAC + ABAC + ReBAC
数据隔离采用分级策略
```

这些内容现在的作用是帮助你学习和发现问题，不代表已经最终定案。等这张能力地图和术语体系学习清楚后，再进入具体系统设计会更稳。
